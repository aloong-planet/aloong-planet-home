§2双层架构：把连续性和吞吐量拆开

所有事件进同一个 Session，上下文最连续，但会被单个 ReAct Loop 的串行速度卡住。每条事件新开一个 Session，吞吐最高，但结果彼此割裂。双层架构让两层各管一头。

Router 层Worker 层
职责人类交互、任务分派、跨任务协调，是全局的序点和记忆在独立上下文里专注完成单一任务
模型较轻量的模型往往够用通常配能力最强的模型
工具不直接执行任务，甚至可以不配 Bash完整执行工具，内部还能开 Subagent 或 Agent Team
对外统一向用户回复不直接面对人，向 Router 汇报
协作中转少数跨任务协同同层通常不直连，靠共同订阅 Thread 发现冲突

和常见的 Agent Team 有什么不同：Team Lead 要深入单个任务、规划子任务、高频协调成员，自身推理负担很重。Router 只处理任务之间的高层关联，不介入单任务内部的拆解。这里的「双层」是逻辑划分，每层内部都可以再有结构。

看这组数字时注意：文章没有定义「分摊时间」，低负载下它是单次请求耗时的 2.5 倍，所以它不等于单次耗时除以 batch 大小。一种可能的解释是一个决定要用多次请求，这是调研时的推断。40 条/分钟是最高测试点，真正的上限没有测到。

§3事件驱动：让环境推着 Agent 走

驱动 Agent 的主要输入，从人类逐条键入的提示词，变成群聊消息、邮件、日程提醒、评审评论、CI 结果这类半结构化事件，统称 Trigger。一条 Trigger 的生命周期要回答四个问题。

§3.1 过滤
环境事件噪音高、触发率低。程序层用确定性规则筛掉大部分消息，语义层再由 LLM 判断。语义层的策略用提示词写，可以随时开关或新增。
§3.2 路由
同一个 PR、IM 话题或邮件串下的连续事件构成一条 Thread。Router 为新 Thread 创建 Worker 后，Worker 订阅这条 Thread，后续事件由程序直达。订阅是多对多的：共同订阅一个 PR 的多个 Worker 收到相同事件，不用点对点通信也有机会自行解决冲突。
§3.3 注入
把上下文窗口当 Cache 管。注入过多会稀释模型注意力，过少会迫使模型反复调用工具。下面这张图是它的完整机制。
§3.4 提前行动
借鉴投机执行，根据环境信号在后台先试，有价值就交付，没价值就丢弃。作者的内部群配了一条「静默复现并修复」策略：只有确认问题并找到简单修复才发声，否则全程安静。

Inline & Spill 和链式召回

三步做法：从最少信息开始，只给 ID 和摘要；按局部性逐步 Inline，比如前 50 字、IM 的相邻消息、同一评审讨论里的相邻评论；超过上限就 Spill，一种简单做法是截断并保留续读入口。

§4面向人的交互：前台不被后台卡住

文章说这个异步机制「已在 DeepSeek Harness 中实现，但尚未默认开启」。核对公开代码：run_in_background 和超时转后台默认都是开的，也没有名为 start() / stop() 的工具。没有默认的是「耗时调用一律异步」：模型不主动放后台时，bash 仍在前台最多等 60 秒。把「未默认开启」理解成这一点是调研时的推断，也可能指未公开的内部配置。

§4.2 输出要匹配信道

信道风格规范
IM 等即时通讯低打扰的轻量沟通，只在需要决策或验收时通知只问直接问题，给简短结论，单次回复不超过 100 词
GitHub、邮件、文档结构化、高信息密度的异步交付PR 写完整的问题背景、改动说明和验证结果；邮件和文档给结构化摘要

§5计算、状态、环境：分两步解耦

这个思路和 Anthropic 的「脑手分离」一致：brain 对应计算，session 对应状态，hands 对应环境。文章自己指出的区别是场景：Anthropic 讲托管服务里的沙箱和客户 VPC 资源，这里首先要接的是可能间歇在线的个人机器。

调研时的推断：这个场景差异会改变故障恢复方式。Anthropic 的容器是可丢弃的 cattle，坏了就换一个；个人机器上有未提交的修改和本地凭据，没法重建。

代价写在 §8.4：云端 Loop 一旦被入侵或被提示词注入攻破，它连接的全部设备都有被控制的风险。作者把这列为开放问题。

§6Watchdog：主系统之外的控制回路

许多异常不是进程崩溃，而是模型陷入无效循环或偏离目标。所以除了基础设施的存活，还要监控任务本身的进展。可以在总图里回放 Worker 跑偏的场景。

进程存活探测、监控脚本Watchdog Session
监控什么进程是否活着接口报错、状态恢复失败，以及每个 Worker 有没有实质进展、方向是否偏离整体目标
谁来判断预设规则模型
怎么介入告警或重启及时修复；遇到外部偶发故障就持续复查，直到恢复
怎么用它看日志和看板用自然语言问故障原因，让它在线增删提示词、调整触发规则

§7实验：用更多 token 换更短、更稳的完成时间

作者用群聊和 GitHub CI 消息流驱动四种方案。每次约 300 条消息，其中约 20 条是工作请求，每种方案跑 5 次。编码工作用一个只消耗时间的工具替代，所以这里衡量的是调度能力，不是单任务执行能力。

方案P50（分钟）P95（分钟）读缓存 token
Super-agent12.415.72323 万
Super-agent，去掉直通12.615.53177 万
单 Session + Subagent 工具，中性提示20.429.5605 万
单 Session + Subagent 工具，提示优先委派13.829.01082 万
  • 单 Session 的问题在于靠提示词决定分不分工。中性提示下，5 次运行模型一次都没调用 Subagent。提示优先委派后有 4 次委派，剩下 1 次判断工作「很小」自己做，形成长尾。
  • 直通省的是 Router 开销。去掉直通后完成时间基本不变，但 Router 要做的决定多了约 30%，读缓存 token 从 2323 万增加到 3177 万，增幅约 37%。

读这组数字要带上的限定

  • 作者声明实验基于合成负载和简化环境，结果仅作初步参考。
  • 累计完成曲线的图注写明消息间隔和工作时长按 1/4 缩放，模型调用耗时是真实值。表格没有单独说明，按同一组实验理解，分钟数不是真实耗时。
  • 每种方案只跑 5 次，没有给置信区间。提示优先委派方案的 P95 主要受 1 次长尾运行影响。
  • 正文说直通「不提高任务完成质量」，但编码被替换成只消耗时间的工具，实验里没有质量指标。
  • 公开仓库里没有实验负载和脚本，无法复现。

公开原型实现了多少

对照 dsh-superagent-prototype@6337fc8 的静态阅读结果，没有运行代码。它是一个面向单个 GitHub 仓库的主动编码 agent，README 明确写了「研究原型，非 DeepSeek 正式产品」。路由内核（§2 到 §4）基本都有，§5 和 §6 的主体在这个版本里没有看到。「本次检索未见」来自全仓多同义词检索，不代表内部版没有。

代码里多出来的一层：文章没有画确定性控制面，原型却以它为核心。Engine 是 Trigger、Thread、Decision、Ticket 的唯一写入者，方法全部同步。LLM Session 负责决策，序点实际落在 Engine 上（后半句是调研时的推断）。读代码时注意术语：文章的 Router 在代码里叫 orchestrator，订阅的主体是 Ticket，Worker 是 Ticket 的执行者。

§8作者自己列的开放问题

  • 怎么扩展双层架构。Router 何时切分、粒度多大，Worker 何时需要直接通信，都没有定论。运行周期拉长到跨月后，长程记忆是主要瓶颈。
  • 脱离 Session 后怎么协作。聊天窗口有路径依赖，交互可以更多发生在领域特化的界面里，比如 GitHub。用户中途介入和接管的方式还要探索。
  • 上下文边界和 A2A。共用一个实例就是共享上下文。多个隔离实例之间怎么安全通信，比如个人助手和团队 Super-agent 之间。
  • 安全与隐私。事件驱动带来更多不可信输入，云端和端侧的连接默认互相信任。作者认为，这个问题解决不好，Super-agent 只能在很小的可信范围内工作。
