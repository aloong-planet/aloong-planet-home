# Deployment

## Local release

Use Node 26.7.0 or later and pnpm 9.12.3. Keep the lockfile committed. The homepage is the workspace package `@aloong-planet/home` in `apps/home/`; install once at the repository root, then run its commands from `apps/home/` or, from the root, through `pnpm --filter @aloong-planet/home run <script>`, as the workflows do.

```sh
pnpm install --frozen-lockfile
pnpm --filter @aloong-planet/home run cf:login
pnpm --filter @aloong-planet/home run cf:deploy --dry-run
pnpm --filter @aloong-planet/home run cf:deploy
```

The login command opens Cloudflare OAuth, requests account/user read plus Pages/D1 write, and stores the credential in the OS keychain. Login is a one-time setup until authorization expires. Never paste credentials into source files or chat. CI uses an API token instead of interactive OAuth.

`cf:deploy` requires a clean Git checkout and uses the existing project/database in `apps/home/wrangler.jsonc` and account in `apps/home/deployment.config.json`. It runs type checking, all tests and the build; confirms the project and database exist; applies pending migrations; uploads `apps/home/dist` to production branch `main`; and checks the deployed revision, pages, images, the not-found page and visitor cookie endpoint on all three hosts. An error stops subsequent steps and returns nonzero. It never creates projects or databases. The dry run checks local configuration and Git state only; it does not authenticate or execute deployment steps.

Public smoke checks do not register synthetic visitors. They check cookie bootstrap and reject a POST without a cookie. Blog pages and the English homepage and Blog page must answer with status 200 and their own expected text, so neither the not-found page nor another page, nor the page's version in the other language, passes for them. `/en` must redirect to `/en/`, and `/en/blog/` and `/en/blog.html` must redirect to `/en/blog`. An address the site does not have must get the not-found page with status 404, and an address under `/en/`, an English post address `/en/blog/<slug>` included, must get the English one. Every image the deployed homepage, the Blog page and the not-found page show, in both languages, the dog's motion frames and the post covers included, must come back with status 200 and an image content type, and the dog script that lists those frames must come back as a script. Content types are checked as well as status codes, because a host without the not-found page answers a missing file with the homepage and status 200. Database registration/concurrency is tested against disposable local SQLite/D1; smoke checks alone do not prove production database writes. A public verification error can occur after an upload has already changed production; inspect the deployment in Cloudflare before retrying. No automatic rollback or database reset is performed.

Migrations run before upload. Keep them additive and compatible with the previously deployed site. A failed upload may leave a successfully applied schema migration in place. The initial `CREATE TABLE IF NOT EXISTS` migration preserves the table created through the dashboard. Do not drop, truncate or reseed production visitor data. `pnpm db:local`, run from `apps/home/`, changes only the local database.

## Agentshed's site

Agentshed's website is the workspace package `@aloong-planet/agentshed` in `apps/agentshed/`. It is published to the existing Cloudflare Pages project `agentshed`, behind `agentshed.aloongplanet.com`, by `pnpm --filter @aloong-planet/agentshed run cf:deploy`, which runs `pages-deploy`, the one command of `packages/pages-deploy/` that the `cf:deploy` of each app site deployed from here runs, with the account, the project, the files the build must hold (`index.html` and `zh/index.html`) and the project's production branch (`main`) from `apps/agentshed/deployment.config.json`. A configuration that lacks any of the four is refused before the command runs anything. The command requires a clean Git checkout. It builds the site, uploads `apps/agentshed/dist` to that branch as the project's production deployment of the checked-out commit, and then reads the project's deployment list and requires the deployment that Wrangler reported to be the production deployment of that commit, on that branch. An error stops the command with a nonzero exit code. It never creates a project.

The production branch in the configuration must equal the project's production branch in the infrastructure repository (`aloong-planet/infra`, where `stacks/apps/landing-pages.tf` sets it): Cloudflare takes an upload to any other branch as a preview deployment, which the command does not accept as the production deployment. A configuration that differs leaves a preview deployment and a failed Deploy run, and the production site keeps its last deployment. No test in this repository compares the two. It runs none of the site's checks, because it runs only after CI has passed, and it requests none of the site's public addresses and does not read a deployment's status. `--dry-run` reads the Git state only. A run by hand uses Wrangler's own login or `CLOUDFLARE_API_TOKEN`.

The project's Cloudflare Git builds are turned off in the infrastructure repository (`aloong-planet/infra`), so this repository is the only place that publishes the site. Cloudflare documents that Wrangler can still upload to a Git-connected project once its automatic deployments are off. If Cloudflare refuses an upload, the site keeps its last deployment and the Deploy run fails. Turning the project's Git builds on again is no way back: its build settings in the infrastructure repository name a `site/` directory that Agentshed's repository no longer has. A refused or bad deployment is recovered by the dashboard's rollback (see Recovery below) and, once the cause is cleared, by re-running the Deploy run.

## JustSnap's site

## The download count's Worker

The download count's Worker is the workspace package `@aloong-planet/download-count` in `workers/download-count/`. Nothing in this repository deploys it. `aloong-planet/infra` deploys its main module and the core beside it from the commit of this repository that it pins, each checked against its pinned SHA-256, so a change merged here reaches the Worker only when infra pins a commit that holds it. This repository's Deploy workflow has no job for the Worker; it publishes the sites, and a push to main that changes only the Worker publishes every site all the same (see the Deploy workflow below). The runbook is `docs/ops/download-count.md` in Agentshed's repository.

## GitHub automation

The CI workflow (`.github/workflows/ci.yml`) runs on pull requests to main and on pushes to main. Its `CI gate` job passes only when every job the run selected succeeded. A push to main runs every check. A pull request runs the homepage checks (install, then type checking, tests and build of `@aloong-planet/home`) and the site width check (see the README) only when it changes a path that `.github/ci/routing.json` routes to the homepage (everything under `apps/home/`), a path every package depends on (the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `packages/`), or a path the file does not list. A change under `apps/agentshed/` runs the Agentshed site checks (the type check, lint, the lint rule's test and the tests of `@aloong-planet/agentshed`, see [its README](../../apps/agentshed/README.md)) and the same width check, not the homepage checks; a change under `apps/justsnap/` runs the JustSnap site checks (the type check and the tests of `@aloong-planet/justsnap`, see [its README](../../apps/justsnap/README.md); no browser is installed for them) and the same width check, and none of the others; a change under `apps/transfer/` runs the Transfer site checks (the type check and the tests of `@aloong-planet/transfer`, see [its README](../../apps/transfer/README.md); no browser is installed for them) and the same width check, and none of the others; a change under `workers/download-count/` runs the Worker checks (the lint and the tests of `@aloong-planet/download-count`, see [its README](../../workers/download-count/README.md); no browser is installed for them) and none of the others, the width check included; a change to a path every package depends on, to anything under `.github/` or to a path the file does not list runs all of them, and no other change runs the site kit checks (the type check and the tests of `@aloong-planet/site-kit`, the parts the sites share; no browser is installed for them) or the Pages deploy checks (the type check and the tests of `@aloong-planet/pages-deploy`, the command that the `cf:deploy` of each app site deployed from here runs, with its process boundary replaced; no browser is installed and no Cloudflare token is used). The checks and the deployment name the package in `pnpm --filter <package> run <script>`: pnpm answers a filter that matches no package, or a script no selected package has, with success, so `.github/ci/workflows.test.mjs` fails when a command names a package or script that does not exist. A change that touches only the documentation paths that the `Documentation` rule of `.github/ci/routing.json` lists skips those checks; a document inside an app's folder, such as `apps/transfer/README.md`, belongs to that app's scope and runs its checks. The repository policy job, which tests the routing in `.github/ci/`, always runs.

The Deploy workflow (`.github/workflows/deploy.yml`) runs after the CI workflow succeeds on a push to main. Its job `deploy` publishes the homepage, its job `deploy-agentshed` publishes Agentshed's site, its job `deploy-justsnap` publishes JustSnap's site and its job `deploy-transfer` publishes Transfer's site; each deploys only that revision, and only while it is still the tip of main. A push deploys every site, whichever of them it changed: CI selects every scope on a push, so the run has nothing to tell them apart by. The jobs are independent, so one site's failed deploy leaves the others' standing, and each has a concurrency group of its own (in a shared group, a newer run's pending job would cancel the older run's pending job of another site). Deployments of one site are serialized. Pull requests receive no Cloudflare token and perform no remote deployment. A fresh homepage deployment runner repeats the same local validation command before publishing; the Agentshed, JustSnap and Transfer jobs do not, because their checks ran in the CI run they follow. To redeploy, re-run the Deploy run, or only its failed job, in GitHub Actions; there is no manually triggered workflow.

Both workflows give their token read access to the repository only. A job that needs more declares its own `permissions`, so the extra access stays with that job and is reviewed with it.

One repository Actions secret is required:

| Name | Value |
|---|---|
| `CLOUDFLARE_API_TOKEN` | Cloudflare token scoped to account `7f1ceca4bab4b98d5d778e1231d7abaa`, with Cloudflare Pages Edit and D1 Edit; the Pages permission covers every Pages project of the account, `agentshed`, `justsnap` and `transfer-org` included |

Create the token through the Cloudflare dashboard, selecting only the existing account. Set it through GitHub Settings → Secrets and variables → Actions → New repository secret, or `gh secret set CLOUDFLARE_API_TOKEN --repo aloong-planet/aloong-planet-home` (interactive hidden input). Do not pass the token as a command-line argument or commit it. Account/project/database identifiers are already configured and are not secrets. No DNS-edit permission or paid Cloudflare plan is required by the Deploy workflow.

Without the secret, checks still run but the Deploy workflow fails with a setup message. Automatic deployment also requires GitHub Actions to be available under the account's current allowance. There is no paid-plan upgrade or spending-limit change in this setup.

The repository is public. The ruleset on main requires the `CI gate` check, and it is the only required check. Do not require the homepage checks or any other job by name: whether those jobs run depends on what a pull request changes, and `CI gate` already accounts for them. Deployment is never a required check. Follow the [project's merge policy](documentation-merges.md) for approval requirements.

The Pages configuration schema does not accept `account_id`. The deployment command reads the account from `apps/home/deployment.config.json` and supplies `CLOUDFLARE_ACCOUNT_ID` to Wrangler. Public verification hosts are defined in that same deployment settings file. Agentshed's, JustSnap's and Transfer's commands do the same with `apps/agentshed/deployment.config.json`, `apps/justsnap/deployment.config.json` and `apps/transfer/deployment.config.json`, which also name their Pages projects, the files their builds must hold and their projects' production branches.

## Build output and environments

- `apps/home/public`, the selected `apps/home/assets`, the homepage, Blog page and not-found page of each language rendered from the dictionary `apps/home/public/ui.js`, the blog generated from `apps/home/content`, and the compiled function become `apps/home/dist`. A post the build refuses stops the build, and so the deployment.
- Build emits a plain JavaScript `_worker.js`, checks its syntax and records the Git revision in `deployment.json`. Never upload Wrangler's multipart `--outfile` output as JavaScript.
- `_routes.json` restricts function execution to `/api/visitor`; the rest is static.
- Only production binds the existing D1 database. `env.preview.d1_databases` is explicitly empty. No preview deployment is automated. Configure a separate preview database before testing its counter.
- Local development uses isolated `apps/home/.wrangler` storage, not production data.
- `docs`, `apps/home/tools`, raw photos, secrets, test logs, node_modules and local databases are excluded from the deployment.

## Recovery

Cloudflare Pages retains prior deployments. To recover the site, select a previously successful production deployment in the dashboard and use its rollback action after reviewing the target. Rolling back Pages does not roll back D1. Do not delete the existing project or change custom domains to fix an upload failure.
