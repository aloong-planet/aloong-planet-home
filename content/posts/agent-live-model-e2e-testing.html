刚开始用 Codex 开发微信插件时，我经常遇到一种落差：测试报告里已经全部通过，真正拿到微信里使用，结果却和预期不一样。

这个插件的入口是微信里的 Clawbot，可以定时推送信息、整理笔记，也可以按要求查找和发送文件、图片。我的需求看起来并不复杂，但交付时常常要反复磨合：Codex 完成修改，单元测试和 E2E 都跑通了，我发一句消息，却发现它没有正确理解要求，或没有完成应有的操作。把问题反馈回去，再修改、再测试，往往要经过几轮，才能达到最初设定的目标。

后来，我把真模型端到端回归加入了交付流程：不只检查工具能否执行，还让真实模型接收用户口令、处理连续对话，再核对最终发生了什么。这让不少原本要等我使用后才暴露的问题，提前在开发阶段被发现和修复。目前目标达成率接近 100%。

前面的《聊一聊Agent开发中的语义化测试替代方案》，介绍了如何通过结构化输出，减少“意思答对了，却因措辞不同被测试判错”的问题；《聊一聊 OpenTelemetry 在 Agent 开发中的作用》，介绍了如何用链路追踪串起执行过程，让开发 Agent 更容易定位故障。这两项是判断结果和排查问题的基础，具体实现可以回看前文。这一篇重点说说：怎样把它们用在真实交互测试中，缩小“测试通过”和“交付符合预期”之间的差距。

为什么测试都通过了，交付仍然不符合预期

这里先区分两个角色：业务 Agent 是插件里响应微信消息的模型；开发 Agent 是帮助我读代码、运行测试、定位问题和修复缺陷的 Codex。本文讨论的，是后者如何测试前者及其背后的完整系统。

后来回头检查，我发现问题不在于“有没有 E2E”这个名字，而在于它到底覆盖了什么。我的系统既有模型决策，也有权限、文件沙箱、工作流和消息发送。单个模块正确，不能自动推出整条交互正确。

首先，工具能工作，不代表模型会正确使用它。“把相册中最新一张图片发给我”，需要模型理解目录范围，决定查询和排序参数，再把正确的文件交给发送流程。如果测试已经给好了参数、文件引用和工具调用，它验证的是执行能力，却没有验证这些决定能不能由真实模型作出。

其次，一轮操作成功，不代表连续交互也能接上。模型列出两张图片后，用户回答“都要”，系统必须把这句话和之前的候选、待选任务以及权限上下文联系起来。只分别测试“列出图片”和“发送两张图片”，就可能漏掉中间的衔接。任务改了、用户取消了，旧状态也不能继续影响后续执行。

还有，测试路径和实际使用路径必须对得上。如果测试直接调用底层工具，就无法覆盖消息进入系统后的一系列处理；如果模型输出始终是预设的，也就看不到真实模型可能选择的参数、探索路径和纠错过程。

这并不意味着原来的测试没有价值。单元测试、集成测试和预设模型的 E2E，仍然适合验证确定的规则、接口接线和异常分支。传统 E2E 也可以覆盖复杂状态和实际副作用；我们缺少的，是把真实模型的理解与决策纳入同一条验证链路。

所以，我没有用另一套测试替换它们，而是在此基础上补了一层：从用户会说的话开始，让真实模型参与完整执行，再检查任务有没有真正达成。

把真实交互放进端到端回归

我把这部分称为“真模型端到端回归测试”。它不是再请一个模型给回答打分，而是让真实的业务模型进入被测试的执行链路。

测试程序从专用的模拟微信入口提交口令，进入与生产一致的入站处理，再经过模型会话、工具执行和工作流。查询使用受控测试文件和权限配置，模型需要自己选择工具和参数，测试不替它预先安排决定。

外部微信渠道在自动化阶段采用模拟实现，记录本来要发送的内容，不真的把每一轮回归消息发到我的手机。因此，这里说的“一致”是应用内部处理链路一致，不是把模拟通道冒充真实微信网络。

整个过程可以概括为：

用户口令 → 生产一致的入站链路 → 真实模型自主调用工具 → 实际文件操作与工作流 → 模拟发送记录 → 结论和证据核对。

传统的单元测试、集成测试和预设模型测试仍然保留。真模型回归是在它们之上，专门补上“模型如何使用系统”的验证。

第一，测试用户会说的话，而不是只测工具参数

其中一个真实模型回归口令就是：

把相册中最新一张图片发给我

测试不直接调用文件查询或发送函数，而是把整句话交给真实模型。随后检查：是否选中测试数据里最新的那张图片，是否只发送一张，以及是否没有多余地进入候选选择流程。

如果工具都能工作，但模型选错目录、没有排序，或者把唯一结果又交给用户选择，这个交互仍然不符合预期。

第二，多轮上下文必须连起来测

我们有一组固定回归场景，第一轮口令是：

帮我找 Pictures 里的 album 图片，先列出来让我选择，暂时不要发送；我可能会选多张。

模型通过工具进入候选选择流程后，第二轮回复：

都要

第一轮不应该发送附件。第二轮则应该恢复同一个待选任务，发送两张候选图片，每张一次，然后结束等待状态。

只单独测试“都要”这两个字，没有前一轮的候选和任务状态，是验证不了这个功能的。因此，同一用例的多轮交互共享上下文，不同用例则隔离服务、状态和诊断目录，避免旧任务影响新场景。

同样的第一轮，还可以接不同的后续回答：

  • “我改主意了，这个就先放着吧”：取消待选操作，不发送图片。
  • “这两张都不要了，帮我把 Pictures 里的 holiday 图片发给我”：结束旧任务，处理新的目标。

这些不是把几个关键词写成宿主判断规则，而是让真实模型参与意图理解，再核对系统有没有执行正确的状态变化。

第三，允许不同路径，但不能放宽结果要求

我们曾经遇到一个很典型的测试误报：模型成功完成了原文件发送，但测试失败了，因为测试预期调用两次工具，实际却调用了五次。

其中有一次读取使用了无效引用，模型随后重新查询，最终完成发送。前面的工具错误需要保留和分析，后面的恢复成功也应如实记录。

因此，真实模型测试不再把某条固定调用路线当成唯一正确答案。我们核对实际工具记录与 Trace 是否一致，再检查必要的执行行为和最终副作用。

模型可以调整查询，但不能越过授权范围；可以多查几次，但不能多发文件；可以从错误中恢复，但不能把没有完成的工作说成完成。

固定的是业务约束，不是模型的每一步探索。

怎样判断它真的把事情做对了

只检查回复“文件已发送，请查收”，仍然不够。对我们来说，一次交互需要同时回答三个问题。

第一，业务结论是否符合预期。主模型负责最终答复时，检查本轮的结构化 results。如果是工作流接管并返回执行回执，则以工作流记录为准，不强求再补一份模型结论。

第二，实际产生了什么副作用。核对选中的文件、发送数量与顺序、工作流状态和逐项发送结果。要求两张就不能只发一张，也不能靠历史发送记录凑够两张。

第三，不该发生的事情是否确实没有发生。用户取消后不能继续发送；要求“只修改，不发送”，就要同时验证修改结果和没有新增外发；没有找到文件，不能悄悄换到其他目录发送一个相似文件。

“没找到”的测试也要有正向对照。我们会在同一上下文里，先要求查找不存在的图片，再要求发送一张确实存在的图片。这样既防止一直回答“没找到”也能过关，也检查后一轮有没有误用前一轮的结论。

结构化输出提供业务结论，Tracing 提供执行过程，文件与工作流记录提供实际结果。它们互相核对，而不是让模型只凭一句“完成了”证明自己。

把一次验证变成可以重复执行的回归

这套测试并不是每次临时聊几句、看着差不多就结束。

我们把已经确认的场景保留为固定用例。新功能增加对应场景，修复缺陷时补充能复现问题的用例，再复用已有入口、隔离机制和断言，重复检查受影响的行为。

交付前，开发 Agent 先执行针对性测试，再运行完整工程门禁以及相应的真模型回归。失败时，结合结构化结论、Trace 和实际执行记录判断：是产品行为有问题，还是测试断言测错了对象。修复后重新运行，而不是原样重复直到碰巧通过。

测试结果还必须形成报告，至少保留这些信息：

  • 测试对应的版本、范围和执行命令。
  • 完整口令与实际回复原文，不能只写“发送成功”。
  • 任务状态、关键步骤、逐项执行结果和模拟发送记录。
  • 哪些检查通过、哪些失败或未覆盖，以及真实微信还需要确认什么。

报告让“测试过了”变成可以复核的证据，也让我能够在微信里使用相同口令确认结果。

自动化阶段得到的是候选通过；真实微信阶段，再核对相同业务结论与实际文件接收效果。自然语言不要求逐字一样，但业务行为必须一致。渠道接受发送与手机实际收到，也分别记录。

把问题留在交付之前

引入这三项实践后，最明显的变化不是测试报告更漂亮，而是交付更可靠了。

结构化输出让测试能够判断模型的业务结论，而不被措辞变化干扰；OpenTelemetry Tracing 让失败有迹可循；真模型端到端回归则把这些能力放进完整交互中，检查 Agent 是否真的理解要求、正确调用工具，并产生预期结果。

在目前已经交付并由我验收的功能中，这套流程落地后，功能都在第一次真实微信验收时达到了预期。

这里的“一次成功”，不是开发过程没有失败，而是失败更多地发生在交付之前，被测试发现、定位和修复，不再需要我反复充当测试员。因为大模型一定程度上已经是一个非常优秀的测试员。未来很可能会成为唯一的测试员。
