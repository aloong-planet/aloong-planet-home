先说结论：把 Claude Code 升级到最新版（写这篇时是 v2.1.318），一般运行 claude update 就行，其他安装方式见后文。

新版多了一个功能叫空闲压缩（idle compaction），对应的配置项是 idleCompaction。它解决一件很贵的事：上下文已经很大的时候，你离开超过一小时再回来。

用订阅的话，升级后什么都不用配，它默认就开着，省的是额度。用 API Key 或云厂商的话，默认不会触发，要先改缓存时效，这笔账得另算，后面会讲。

我 10 月用的是 v2.1.286，11 月初升到 v2.1.317，正好前后各有一批记录。我把这些记录拆开算了一遍：

  • 回来这一下：28 次真实记录，不压缩估算要约 94 美元，实际约 25 美元，少花 73%。
  • 回来之后接着干：这 28 段工作估算少处理约 2.5 亿 token，少了 38%。
  • 整张账单：估计省 8% 到 14%。

我用的是订阅，不按美元扣费。官方文档把缓存未命中列为额度上涨的原因之一，但额度怎么折算 token 没有公开。所以下面的美元都按 Opus 5.5 的 API 公开价折算，只用来比较相对大小，不等于额度也能省同样的比例。

为什么离开一小时这么贵

模型没有记忆，Claude Code 每发一次请求，都要把整段上下文重新发一遍。prompt cache 让这部分变便宜，但读和写的价格差得很远：

动作相对普通输入的价格50 万 token 要花
读缓存0.05 倍0.10 美元
写缓存（1 小时有效）2 倍4.00 美元

同样 50 万 token，写是读的 40 倍。Sonnet 5.5 也是这个倍数。

订阅用户的主会话，缓存默认保留 1 小时。只要一小时内有请求，缓存就续上了，每轮只付读的价格。一旦离开超过一小时，缓存过期，你回来说的第一句话哪怕只是「继续」，整段上下文也要重新写一遍。

我查了自己的记录。10 月里，上下文 20 万以上、离开超过一小时再回来的情况有 141 次，每次第一个请求的中位数是 4.38 美元，合计 629 美元，占当月账单的 8.4%。

空闲压缩做了什么

会话空闲约 54 分钟时，Claude Code 趁缓存还没过期，自动发一个请求，把对话压缩成摘要。我这边 35 次记录全都发生在最后一次请求之后 53.3 到 54 分钟，耗时中位数 71 秒。

这个请求读的是缓存，所以便宜。等你回来，要写进缓存的只剩摘要和重新载入的内容。

以 50 万 token 为例：

  • 不压缩：整份重写，4.00 美元。
  • 空闲压缩：读缓存 0.10 美元，生成摘要约 0.20 美元，回来重写约 8 万 token 要 0.63 美元，合计 0.93 美元。

回来这一下省的其实不是 token 数量，这 50 万一样要过一遍，省的是单价。数量要到后面才开始省。

实测省多少

回来这一下：少花 73%

升级后有 28 次离开再回来，全都过了一小时才回来，所以缓存确实会过期。同样这 28 次，如果没有空闲压缩，第一个请求合计约 94 美元；实际花了约 25 美元，其中压缩请求约 8 美元。

压缩请求的用量不写在会话记录里。它读缓存的量是确定的，生成摘要的输出量是我按 1 万 token 估的。按 5 千到 2 万算，这个比例在 67% 到 76% 之间。

不压缩的费用跟着上下文线性涨，压缩后基本平在 1 美元左右。所以上下文越大，省的比例越高：

离开前的上下文不压缩空闲压缩少花
20 万1.60 美元0.87 美元45%
50 万4.00 美元0.93 美元77%
80 万6.40 美元0.99 美元84%

这张表里，回来要重写的量按我的中位数 8 万算，我的规则文件和记忆比较多。如果你的只有 3 万，三档分别是 70%、86%、91%。

回来之后：每轮读得少，但要补读

压缩之后上下文小了。我回来时上下文的中位数是 10.9 万，之后每轮读缓存的量也跟着变小。

但摘要会丢细节，Claude 可能要把一部分内容重新读回来。回来后的 20 个请求里，压缩过的会话上下文涨了 12.2 万，没压缩的只涨 5 万。这个差距不全是读回来的：两组做的不是同一批任务，我的规则还要求压缩后重新载入用到的 skill，别人未必有这笔。我把差的这部分都算成压缩的成本。它要按写缓存的价格付钱，所以省的比例不会一直停在 77%：

按这组中位数算，30 个请求后的差距从 3.07 美元变成 4.12 美元，还是少花一半多。这只能当作近似。

直接数 token 也能看到差别。这 28 段工作实际处理了 3.96 亿 token，包括压缩请求读的那一遍；不压缩的话估算要 6.43 亿，少了 2.5 亿。

整张账单：8% 到 14%

口径账单省下比例
11 月 3 日至 5 日，真实记录1,045 美元约 93 美元约 8%
10 月，假设每次都压缩7,522 美元约 1,053 美元14%

第一行的账单已经是省过的，比例按「账单加省下的」算。两行都扣掉了压缩请求本身和读回来的内容，第一行还扣掉了没回来的压缩。换不同的假设（摘要的输出量、读回来的量），第一行在 6% 到 10%，第二行在 11% 到 17%。

这个比例很看习惯。我的上下文偏大，10 月那 141 次的中位数是 57 万，又经常让会话停着等我。回来第一个请求这笔钱，在我 7 到 10 月的账单里每月占 8% 到 23%。如果你的上下文很少到 20 万，或者很少离开一小时，能省的会少很多。

想看自己的情况，运行 /usage，Session 部分有一行 Prompt cache (main)，会列出缓存未命中的次数和重写的 token 数。

什么情况下它不会跑

官方文档写的条件是同时满足下面这些：

  • 会话类型：交互式终端、VS Code 聊天面板，或桌面 App 的 Code 标签页（会话跑在本机或 SSH 上）。
  • 自动压缩开着：autoCompactEnabled 没关。
  • 缓存是 1 小时：订阅用户在套餐额度内默认就是。API Key、云厂商，以及超额后走 usage credits 时默认 5 分钟，不会触发。API 用户想用，要设 "promptCacheTtl": "1h"，代价是每次写缓存都从 1.25 倍涨到 2 倍，所以这篇的比例不能直接套用，值不值要看你多常离开。
  • 上下文够大：默认 20 万 token。上下文窗口只有 20 万的会话，到不了门槛就先自动压缩了，这种情况可以调低门槛。
  • 电脑醒着：要一直醒到那个时候。

调门槛用这个环境变量，写在 settings.json 的 env 里，最低 10 万：

CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS

最容易踩的是最后一条：合上笔记本走开一小时，它就跑不了。知道自己要离开很久又要合盖的话，走之前手动跑一次 /compact，趁缓存还在，一样便宜。

它的代价

摘要会丢细节。 压缩后 Claude 手里只剩摘要。官方文档写的是：会重新读最多 5 个最近改过的文件，技能正文每个最多保留 5,000 token、总共 25,000 token。读回来的那笔钱能算出来，但丢了细节之后答得有没有变差，我量化不了。做到一半的复杂任务，回来后最好先让它确认一下当前状态。

不回来就白花。 压缩在你离开时就做了，不回来这笔也花了，50 万上下文约 0.30 美元。我 35 次压缩里有 7 次到写这篇时还没回去。算下来，回来的概率超过约 9% 就划算。

回来得太早也亏。 压缩在约 54 分钟就做了。如果你 55 分钟回来，缓存本来还在，终端里的对话却已经换成摘要了；VS Code 和桌面 App 只有缓存过期才用摘要。我这 28 次都没碰上，最早的一次也是离开约 65 分钟才回来。

也不是每次都拦得住。 升级后，上下文 20 万以上、离开超过一小时的有 36 次，35 次压缩了，1 次没触发，原因我没查清。

不想要可以关掉：在终端里运行 /config，改 Idle compaction 这一行；或者写进 settings.json：

{
  "idleCompaction": false
}

怎么升级

# 看当前版本
claude --version

# 原生安装
claude update

# npm 安装
npm install -g @anthropic-ai/claude-code@latest

Homebrew 的 claude-code 跟的是 stable 渠道，要最新版得装 claude-code@latest。已经开着的会话不会变，重启后才用上新版。

建议直接升到最新，因为这个功能是分几个版本补齐的：

版本变化
v2.1.290配置项 idleCompaction 从这版起生效
v2.1.299终端加入空闲压缩，changelog 第一次写到它
v2.1.302/config 增加开关
v2.1.314支持 VS Code 和桌面 App；关了遥测的订阅用户也能跑；Bedrock、Vertex、Foundry 和 LLM 网关开了 1 小时缓存后也能跑
v2.1.318修复空闲压缩可能把对话替换成一段不是摘要的回复

最后一条修的是这个功能本身的问题，所以我建议到 v2.1.318。另外，如果你的环境取不到 Anthropic 的功能开关，比如关了遥测，v2.1.314 之前这个功能根本不会跑。

用 stable 渠道的注意一下：写这篇时它还在 v2.1.311，后两条都没有。可以等它跟上，也可以在 /config 的 Auto-update channel 切到 latest。

升级后想确认它跑过，看提示就行。终端里有一行 Compacted while idle, before the prompt cache expired，VS Code 和桌面 App 的提示里有 a summary written while you were away。

这些数字怎么来的

  • 数据：我这台机器上 2,833 个主会话和 829 个子 agent 的记录，2026 年 6 月 23 日到 11 月 5 日。一个 message.id 算一个请求。
  • 离开再回来：相邻两次请求隔了一小时以上，离开前上下文在 20 万以上，回来第一个请求写缓存的量超过上下文的一半。
  • 不压缩的对照：第一个请求按整份重写算。之后每轮多读「离开前的上下文 − 回来时的上下文 − 7.2 万」，一直算到下一次离开超过一小时或下一次压缩。7.2 万是两组记录在 20 个请求时的增长差，算作读回来的量，它本身还按写缓存的价格计一次。
  • 样本的局限：11 月的记录只有两天多。10 月那一行假设 141 次都能触发，经常合盖或关机的人会打折扣。
