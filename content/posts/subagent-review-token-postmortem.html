以前我的开发流程里，code review 和 test review 都是主 agent 自己做：写完代码，回头审自己的代码，再审自己写的测试。用久了就发现一个问题——审测试这一步，相当于自己给自己判卷。用例怎么设计、断言测的是什么，它写的时候怎么想，审的时候还是怎么想；测错了对象、根本红不了的假通过测试，往往被它自己合理化过去了。

所以最近我把 test review 改成了对抗性测试（code review 仍由主 agent 自己做）：实现完成后，派一个不继承当前对话的独立子 agent 来审写好的测试。交给它的只有规范、spec、测试审查记录和本次改动的提交范围，不给任何「我为什么这么写」的解释。它不知道作者的推理，也就没有替作者圆场的动机，找出来的问题明显多了，测试质量也上来了。

然后我用这套新流程做了一个大需求：给我的桌面应用接入一个新的 agent 来源，拆成六张票，每张票交给一个子 agent 在全新的上下文里实现，每张票做完再派复核子 agent 做对抗性复核，最后一张收口票做全量验收。睡前启动，让它自己跑一晚上。

早上起来一看用量，人傻了：一个晚上，18 亿 token。

需求是做完了，六张票全部合并，质量也确实不错。但这个数字明显不对劲。于是我花了一天，把这一晚的账一笔一笔拆开。

先说结论：这 18 亿里，有 2.6 亿 token（14.4%）是多花的，全花在了「等」上——子 agent 在等测试跑完、等复核子 agent 交回的时候，一遍又一遍地查进度，最密的时候每 4 秒查一次。折成钱更扎眼：约 107 美元，占这一晚的 21%。下面讲这笔账是怎么算出来的、为什么会这样，以及怎么解决。

先把账算清楚：18 亿 token 花在了哪

Claude Code 会把每个会话（包括每个子 agent）的完整记录存成 jsonl 文件，每一次 API 请求都带着用量字段：读了多少缓存、写了多少缓存、输入输出各多少。所以不用猜，直接写脚本把这一晚所有记录汇总：

我用的是订阅，不按美元扣费；订阅额度怎么折算 token，官方没有公开。这里的美元按 Opus 5.5 的 API 公开价折算，只用来比较各部分的相对大小。

第一个发现就很关键：18.1 亿 token 里，98.5% 是缓存读。

这说明钱不是花在「生成」上，而是花在「重读」上。大模型没有记忆，每次工具调用，都要把整个上下文重新发一遍。prompt cache 只是把这部分的单价降到普通输入的二十分之一，读的量一点没少。所以：

消耗 ≈ 调用次数 × 每次的上下文大小

做票 agent 的上下文从 4.3 万 token 起步，做完一张票涨到 89 到 97 万。越往后，哪怕只是执行一条 wc -l，也要为将近 100 万 token 的上下文付一次费。

再把每一次请求按用途分类：只为等待而发出的请求——查进度 328 次、等待命令 49 次——一共花掉 2.6 亿 token，占 14.4%，这就是开头说的多花的部分。其中收口 agent 一个就占了 1.75 亿，是它自己用量的 46.5%。

最大的窟窿：一个子 agent 每 4 秒查一次进度

按 agent 排，花得最多的不是写代码的做票 agent，而是收口 agent：80 美元，比最复杂的那张票还多。收口票几乎不写代码，主要是全量验收和文档回归，它到底在干什么？

把它的 539 次请求按时间线摊开，答案一目了然：它在等。它要等两次复核子 agent 交回结果，等两次全量门禁跑完。在这五段等待里，它一共查了 212 次进度，每一道竖线是一次查看：

复核那两行的金额里含有它同时在做的文档修改；单算纯查看的 193 次，约 35 美元，占它全部花费的 44%。

查的是什么？

  • 等复核子 agent 时：数复核子 agent 正在写的测试审查记录有多少行。光 date; wc -l < 记录 这一条就跑了 43 次。顺带还查进程、查构建产物的修改时间，看对方是不是在跑测试。
  • 等全量门禁时：grep -c "✘" 日志 数失败用例，同一条命令跑了 75 次，平均 4 秒一次。

最讽刺的是，我的流程规范里早就写着：复核以子 agent 的最终交回为准，不得以记录被写入作为结束信号。它没有违反这条——它不是拿行数当结束信号，它只是一直盯着看。规范管住了结论，没管住「看」这个动作。

你可能会问：查得这么勤，缓存一直是热的，每次不是很便宜吗？确实，整个收口过程缓存一次都没过期。但每查一次，就是一次完整的 API 请求，要把 95 万 token 的上下文读一遍，约 0.19 美元。便宜的是单价，次数照乘。同样一段 6.8 分钟的门禁，三种等法的账：

而且这个轮询是它自发的。记录里没有任何外部消息催它，是它自己挂上监视器和循环去盯记录变长。Claude Code 内置的 Agent 工具说明里本来就写着「不要 sleep、不要轮询、不要主动查进度」，没拦住。我后来查社区，发现这不是个例：好几个 issue 都报告过，把「不要轮询」写进提示词能减少轮询，但杜绝不了。

第二个窟窿：子 agent 的缓存只有 5 分钟

查完收口 agent，我有个疑问：主会话在等子 agent 的时候，也经常空闲一二十分钟，为什么主会话就没这个问题？

答案在缓存时效上。Claude Code 的文档写得很清楚：订阅额度内，主会话的缓存保留 1 小时，子 agent 只有 5 分钟，订阅也一样。我用主会话的记录验证了一遍：空闲 60 分钟以内醒来，50 次全部是缓存读；超过 66 分钟的 5 次，全部整份重写。分界线正好在 1 小时。

子 agent 空闲超过 5 分钟再调用，就要把整个上下文重写进缓存，单价是读的 25 倍（token 数不变，所以没算进前面的 2.6 亿，但钱要多付）。这一晚子 agent 一共重写了 18 次，都发生在 5.8 到 12.9 分钟的等待之后，约 54 美元：

在等什么次数折合（美元）
自己派出的复核子 agent926.4
自己的门禁和 CI725.3
复核 agent 交回后被再次唤醒23.5

等复核的那 9 次，多数是做票 agent 在前台挂一条 10 分钟的命令，等复核记录里出现某一节——既是在盯记录，又因为阻塞超过 5 分钟，醒来要整份重写。

到这里，问题的结构就清楚了。切到对抗性测试之前，test review 在主 agent 自己的上下文里做，不用等另一个 agent。切过来之后，形成了三层：主会话派出做票 agent，做票 agent 再派出复核子 agent。等待被夹在了中间那一层：它是子 agent，缓存只有 5 分钟；它又要等另一个子 agent，一等就是十几分钟。轮询和缓存过期，全部发生在这一层。

对抗性测试本身没有错，错在我切换流程的时候，只设计了「谁来审」，没设计「怎么等」。

几个差点走偏的判断

排查过程中，有几个看起来很合理的方向，算完账发现都不对。

第一，「把子 agent 的缓存也改成 1 小时不就行了？」Claude Code 确实提供了 subagentPromptCacheTtl 这个设置。但 1 小时缓存的写入要比 5 分钟的贵 60%，而且是所有写入都贵，不管等不等。用这一晚的数据重算：18 次短空闲不再重写，省 51.4 美元；所有子 agent 的日常写入涨价，多付 39.6 美元，其中 17.8 美元来自 14 个从没过期过的 agent；两次超过 1 小时的限流中断照样重写，单价还更高，多付 5.3 美元。净省 6.5 美元，不到总花费的 2%。等改了等待方式之后，能省的部分进一步缩小，全局开 1 小时反而要多花约 10 美元。

至于订阅额度会不会对 1 小时写入多扣，我专门查了官方文档和社区：没有人给出过答案。唯一的官方说法来自 Claude Code 负责人，他说子 agent 很少被重新唤醒，用 1 小时缓存会让用户「多付钱」。所以这条路我放弃了。

第二，「是不是模型太贵，换便宜的就行？」换模型只降单价，不降次数。轮询是行为问题，换什么模型都会轮询。

第三，几个我原本以为的事实，查文档后发现是错的：前台命令超时不会被杀掉，而是自动转入后台继续跑；后台命令「30 分钟自动终止」只对无人值守的会话成立，本地终端里后台命令没有时限，一个永远等不到条件的后台循环永远不会退出，也就永远不会发完成通知；Opus 5.5 的缓存读是普通输入的 0.05 倍，不是 0.1 倍。这些细节直接影响「怎么等」的方案设计，凭印象就会设计错。

怎么解决：把「怎么等」写成规则

轮询是行为问题，所以要在规则里明确禁止它，并写清楚每一层该怎么等。最后的方案分三部分。

第一部分：全局规则「等待后台工作」

写进全局 AGENTS.md，Claude Code 和 Codex 都会加载，子 agent 也会加载（我在子 agent 的记录里核实过）。要注意，子 agent 拿到的是父会话启动时缓存的那份，会话中途改了规则，要到新会话才生效。核心只有四条：

  • 不得查看进度：等子 agent、自己的命令或 CI 时，不得用任何方式查看进度——读它正在写的文件或日志、数行数、查进程、查 CI 状态都算。结束后读结果不算。
  • 主会话：耗时的命令和子 agent 放后台，没有别的事就结束本轮，等完成通知。主会话缓存 1 小时，被唤醒只付一次缓存读。
  • 子 agent 等待（等自己的命令或派出的子 agent）：不得靠结束本轮来等；每次调用最多阻塞 3 分钟，只检查命令是否结束（比如命令结束时写下的完成标记），等子 agent 时什么都不查；没结束就再等一次；成败按命令自己的退出码判定。
  • 等外部状态（CI、部署）：用一条条件满足即退出、自带超时的命令，按上面的方式等它。

为什么子 agent 是「每次最多阻塞 3 分钟」，而不是像主会话那样结束本轮？因为子 agent 的缓存只有 5 分钟。结束本轮去等，一旦等超过 5 分钟，醒来就是一次整份重写；而每次阻塞 3 分钟，醒来时缓存还在，只付一次读。阻塞期间检查完成标记的是 shell 里的循环，不经过模型，不花 token。

第二部分：流程改动

两处：

  • 单票只跑相关的 e2e：以前每张票的全量门禁都跑全套 e2e，这是最长的等待来源之一。现在单票只跑和本次改动相关的 e2e 用例，全套交给 PR 的 CI 跑，交付前等 CI 全部通过。
  • 点名「看记录」也算查看进度：在复核流程里写明，复核子 agent 交回之前去读测试审查记录，就是在查看进度。

第三部分：不改缓存时效

子 agent 保持默认的 5 分钟。理由前面算过了：在新的等待方式下，改成 1 小时只会更贵。

测试：同一个任务跑八遍

规则写完不能只靠感觉，得测。我把收口环节的两段等待做成了一个可重复的任务：先跑一个约 7 分钟的模拟门禁，再派一个约 8 分钟的模拟复核子 agent，边跑边往记录里追加发现。每组一个父 agent 加一个复核子 agent，先分三种条件各跑两次：没有规则、规则带具体命令、规则精简版（只讲约束，不教命令），规则都写在提示里交给 agent。

测试里的上下文只有 5 万 token 左右，所以我按请求数和缓存过期次数，折算到 90 万上下文（一次读约 0.18 美元，一次重写约 4.5 美元）：

图里没画的两项：没有规则的一组中，有一个复核子 agent 用监视器盯着记录，被唤醒了 7 次；三种条件的总耗时分别约 16、16、20 分钟。

几个结论：

  • 等待的费用降了约九成：精简版规则下，子 agent 自己写出了带完成标记的有界等待，全程没有一次缓存过期。
  • 结果更可靠：没有规则的一组提前交回了，报告里没有复核结论。原因从记录里看得很清楚：它的复核子 agent 结束本轮去等脚本，系统随即发出一条中途通知，父 agent 收到后被要求交回，交出了半成品。这是社区里已经有人报告过的 auto 模式问题。有了规则，子 agent 从不结束本轮，这条通知根本不会产生。
  • 少打扰主会话：没有规则时有 7 条中途通知唤醒主会话，每条都让主会话把整个上下文读一遍。
  • 只讲约束反而更好：精简版不教具体命令，两组都自己写出了正确的等待，标记先写临时文件再改名，比我原来给的模板还稳。

代价是时间：精简版等复核子 agent 时，交回要等当前这段阻塞结束才送到，这次晚了约 3.5 分钟。所以我把每段阻塞从 4 分钟缩到了 3 分钟。

最后用这个 3 分钟的版本又跑了两遍。这次规则不再写进提示，只放在全局 AGENTS.md 里，由新会话里的 agent 自己加载：两遍结果都正确，全程没有查过一次进度，没有缓存过期，也没有中途通知；等待部分约 1.6 到 1.8 美元，和精简版相当；等复核子 agent 时，交回分别晚了 40 秒和 2 分 50 秒。

丑话也说在前面：每种条件只跑了两次，上下文也小。最关键的是，没有规则的那两组并没有复现收口 agent 那种每 4 秒一次的疯狂轮询——小上下文、短任务里，模型的表现要克制得多。所以「禁止轮询能省多少」这件事，证据仍然是那一晚的真实记录，而不是这次测试。

写在最后

回头看，这次的问题不在对抗性测试本身。复核交给独立子 agent，质量确实上去了，我会继续用。问题在于，我切换的是「谁来做」，却没有重新设计「谁在等、怎么等」。

对人来说，等待是免费的：你泡杯茶，回来看结果就行。对 agent 来说，等待从来不是空闲——它每「看一眼」，都要把整个上下文重新读一遍。上下文 4 万时，这一眼几乎不要钱；上下文 95 万时，这一眼要 0.19 美元。而模型对此毫无感知，它不知道自己的每一次「看一眼」值多少钱，只是认真地、负责地，每 4 秒看一次。

所以等待必须被设计：主会话怎么等、子 agent 怎么等、等外部系统怎么等，各有各的最优解，而决定最优解的是缓存时效这种平台细节，不是直觉。Claude Code 内置的说明只写了「不要轮询」，没拦住；这条规则把每一层怎么等都写明了，测试里有规则的六遍，没有一遍查过进度。

如果你也在用独立的子 agent 做复核，又不确定自己有没有这个问题，不妨完整跑一遍流程，再让你的 Claude Code 或者其他 agent 把这次的会话记录（包括每个子 agent 的）复盘一遍：一共等了多少轮、每轮等了多久、等待期间花掉了多少 token。

最后说一个还没解决的问题：等待多花的 2.6 亿只占 14.4%，剩下约 85% 的 token 花在正常干活上。真正的大头，是每个做票 agent 的上下文都从 4 万涨到将近 100 万——整文件读取、一次性加载大量 skill 和 spec，让后半程每一次正常调用都很贵。轮询是最刺眼的窟窿，上下文膨胀才是最大的那块账单。下一篇我们继续聊其他优化。

附：完整的「等待后台工作」规则

下面是我实际在用的规则全文，写在全局 AGENTS.md 里（Claude Code 通过 CLAUDE.md 导入它）。

## 等待后台工作

等待期间每次工具调用都要重读整个上下文；子 agent 的缓存只保留 5 分钟，过期后再调用要整份重写。

- **不得查看进度**：等子 agent、自己的命令或 CI 时，不得用任何方式查看进度（读它正在写的文件或日志、数行数、查进程、查 CI 状态）；结束后读取结果不算。
- **主会话**：耗时的命令与子 agent 放后台；没有与它无关的事就结束本轮，等完成通知。
- **子 agent 等待（自己的命令或派出的子 agent）**：不得靠结束本轮来等。每次调用最多阻塞 3 分钟（Bash 的 timeout 要显式设够，默认只等 2 分钟），期间只检查命令是否已结束（如它结束时写下的标记）；等子 agent 时什么都不查，它的交回会在下一次调用时送到。没结束就再等一次；命令的成败按它自己的退出码判定。
- **等外部状态**（CI、部署）：用一条条件满足即退出、自带超时的命令（如 `/github-ops` 的 `watch-ci.sh`），按上两条的方式等它。
