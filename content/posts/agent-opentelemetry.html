我开发了一个 Codex 插件，用来汇总和整理日常信息。它的交互入口是微信里的 Clawbot：我可以每天收到各种信息推送，也可以把零散的想法、看到的内容和需要记录的事情发给它，让它汇总到我的笔记文档中。

从使用上看，我只需要在微信里发一条消息，但背后的实现并不只是把消息转交给模型。为了控制文件访问范围、隔离不同操作，并让各个模块的职责保持清晰，我引入了权限控制、独立进程和文件沙箱，也把模型决策、工具执行、工作流和消息发送分开处理。

这些设计让系统的边界更明确，同时也增加了执行链路的复杂度。一条看似简单的“把这份笔记发给我”，可能经过消息接收、模型理解、工具调用、沙箱初始化、文件查找、上传和消息提交。其中有些步骤串行执行，有些并行发生，还有跨进程通信和异常恢复。

开发过程中，我主要负责提出需求、测试实际效果，再把“不符合预期”的地方反馈给 Codex。查日志、读代码、分析原因、提出方案和修改代码，则由 Codex Agent 完成。

一条消息发出去，十几秒才收到回复，是模型慢，还是工具慢？要求发送六张图片，实际只收到五张，是少找了一张，还是其中一张上传出了问题？测试报了超时，是服务真的卡住了，还是模型还在正常执行？

面对这些反馈，Codex 往往能提出好几个解释：可能是模型理解错了，可能是工具没有返回完整结果，也可能是发送阶段失败了。接下来，它需要翻服务日志、检查模型交互记录、查询工作流状态，再逐个验证这些假设。

问题不在于 Agent 想不到原因，而在于它缺少足够清晰的证据，无法及时排除不成立的解释。同一次交互的信息散落在不同地方，它每次都要先把执行过程拼出来，才能开始判断。

于是，我给这个 LLM Agent 工具接入了 OpenTelemetry，简称 OTel，通过 Tracing 关联一次交互中的各个执行步骤，并逐步补齐 instrumentation。目的很直接：让负责开发和排障的 Agent 看清问题发生在哪里、时间花在哪里，把时间更多地用在解决问题上，而不是反复猜测。

本文会区分两个角色：工具里的 Agent 负责响应用户，开发过程中的 Codex Agent 负责查问题和修代码。我想改善的，正是后者获取证据、定位和修复问题的效率。

OpenTelemetry 是做什么的

简单说，OpenTelemetry 是一套开源的可观测性框架和工具，帮助程序用统一的方式生成、采集和导出运行数据。它不是大模型，也不是自动诊断助手，更不是自带存储和图表的监控平台。数据后续存在哪里、怎样展示，可以选择不同的工具。来源：OpenTelemetry 官方介绍

本文重点介绍其中的 Tracing，也就是链路追踪。它回答的是：这一次请求经历了什么？各个步骤是什么关系，分别用了多久，又在哪里出了问题？放到这个工具中，就是把一条消息经过模型、工具、沙箱和发送环节的过程关联起来。

Trace 由一个个 Span 组成。一个 Span 可以代表一次工具调用，也可以代表一次网络请求，记录它的开始、结束及相关信息。把属于同一请求的 Span 关联起来，就能看到这次请求的执行路径。来源：官方 Traces 文档

读这张图时，可以把横向理解成时间，把每条色块理解成一个操作。它们的长短、位置和嵌套关系，比一句“总共用了十秒”更有解释力。存在重叠的操作，也不能简单把耗时相加。

而本文说的 instrumentation，就是让程序在合适的位置产生这些观测数据。可以理解为给执行过程装上记录仪，再把记录以 Agent 能查询和关联的方式提供给它。下面重点介绍，我怎样把这套记录能力接入现有的执行链路。

接入前后，Agent 的排查方式有什么变化

接入之前，并不是完全没有日志，而是缺少统一的关联方式。Agent 可以读到一些工具调用和任务状态，却需要自己确认：它们是不是同一轮交互？先发生的是超时，还是进程退出？一次失败影响了几个后续操作？

补齐观测之后，这些关系成为了可查询的字段和事件。Agent 可以先按一次交互或任务定位记录，再向下查看工具、进程和网络请求。

这些能力不是安装 OTel 后一次性得到的。我先关联外层过程，遇到证据缺口后，再补网络协议和沙箱生命周期。真正有用的不是“项目已经接了 OTel”这个标签，而是它是否记录了 Agent 判断问题所需要的事实。

我具体怎么做 instrumentation

我的接入思路是：公共入口集中记录，通用细节自动采集，业务结果显式补充，最后提供统一查询。尽量不在每个业务函数里重复写计时和错误记录。

第一步：把同一次交互关联起来

先观察微信入站、App Server 对外可见的执行阶段、工具调用和工作流。这里的 App Server 是承载模型会话与工具交互的服务。使用 OTel 的 Trace、Span 和异步上下文，把同一轮执行中的相关操作串起来。

关联也不能只靠时间。多个请求可能交错执行，一个工具又可能发起多个发送步骤。我因此保留任务及逐项发送的关联信息，让 Agent 可以从一次交互追到具体任务，再追到其中一项操作。

有了这层关系，Agent 就不必从一大段混杂日志中，仅凭“时间差不多”猜测两条记录是否相关。它可以先确定排查范围，再分析范围内的事实。

第二步：网络细节自动采集，协议结果集中补充

对于受控渠道的 HTTP 请求，我使用 OTel 官方提供的 Node.js HTTP 客户端自动采集插件，在相关业务上下文内定向采集。这样不必在每个请求旁边重复编写开始时间、结束时间和关联代码。

不过，自动网络观测只能看到网络层发生了什么。HTTP 请求返回成功，不代表响应中的业务回执有效，更不代表用户已经收到文件。

所以，图片和普通文件共用的上传链路，还在集中的渠道适配层记录了获取上传地址、上传文件、提交消息等阶段，以及解析错误、提供方拒绝、缺少回执等结果。

这样，Agent 不仅能知道“某次请求失败了”，还能分辨它发生在文件上传还是消息提交阶段，是网络错误、响应解析错误，还是提供方明确拒绝。修复方向不再停留在笼统的“发送有问题”。

第三步：工具调用和批量结果，在统一入口记录

工具标识、等待与执行耗时、结果摘要、业务错误码等信息，放在统一的工具执行边界。文件查找还记录查询条件和扫描完整性等信息，让 Agent 能核对“查的是什么”“是否查完”“结果是否被截断”，而不必为了诊断采集文件全文。

发送多个附件时，还需要记录每一项的序号、总数，以及尝试、接受、拒绝或结果未知的状态。只记录一句“发送工作流结束”，不足以解释用户为什么少收到一张图片。

这些字段把模糊的用户反馈变成了可以核对的问题：选中了几项？尝试了几项？哪一项没有获得确认？Agent 可以沿着具体记录继续查，而不是从搜索、模型选择到发送，把所有模块重新怀疑一遍。

第四步：沙箱生命周期，单独封装 instrumentation

文件操作在沙箱子进程里执行。这里有一个额外的问题：一次“文件查找”，可能同时包含启动进程、初始化、进程间通信和真正执行请求。

只给最外层记一个耗时，很容易把启动成本误认为搜索算法慢。

我因此单独封装了沙箱 instrumentation，集中记录初始化、执行、超时、失效、关闭和退出，并用实例、代际和请求 ID 关联记录。worker 指沙箱工作进程，代际则用于区分重启前后的进程。旧进程迟到的退出通知，也必须记在旧进程上，不能误算成新进程的故障。

除了计时，我还区分首次触发失效的请求和受到连带影响的请求，分别记录失效原因与实际退出信息。这样 Agent 就更容易判断：哪个事件是起因，哪些报错只是后续结果。

这里的执行耗时包含通信、宿主确认及结果校验，不是纯文件算法计时。阶段定义清楚，Agent 才能把数字和正确的代码边界对应起来。

第五步：给开发 Agent 一个结构化查询入口

这是采集之外同样重要的一步。数据存下来了，还需要方便 Agent 使用。

在链路诊断这部分，我把 Span 保存在本地，并补充操作开始和进展的记录，称为 checkpoint。这些 checkpoint 是项目自行补充的诊断记录，并不是安装 OTel 后就会自动产生的。我还提供了只读查询命令，例如，在服务包目录中，Agent 可以按 Trace 或任务查询：

pnpm diagnostics:read --trace TRACE_ID
pnpm diagnostics:read --run INTERNAL_RUN_UUID

读取器返回结构化 JSON，包含记录和关联字段，也包含读取预算是否触顶、是否存在丢弃和未结束操作等信息。开发 Agent 可以据此缩小查询，再结合业务状态和代码分析，而不必先操作一个图形监控面板。

开始和进展 checkpoint 很重要：操作没有结束时，Agent 仍然能知道它已经走到哪一步。若读取结果不完整，则先补足取证，避免把“没读到”误判成“没发生”。

这就形成了完整路径：执行时采集 → 关联成链路 → Agent 查询 → 定位具体环节 → 修改并回归验证。标准采集能力来自 OTel，业务关联、本地存储和查询入口是我为项目补上的接线。

放回我遇到的实际问题，效果是什么

“少发了一张”，不一定是模型少选了一张

我确实遇到过要求发送六张图片，实际只收到五张的情况。

当时已有的证据能看到第一项上传结果未知，后五项被渠道接受，但没有保存足以解释第一项为何未获得确认的底层信息。也就是说，外层状态还在，更深一层的关键证据却缺失了。

这是已有外层观测、但网络细节还没补齐时暴露的缺口。Agent 虽然缩小了范围，仍无法确定未获得确认的具体原因，只能继续检查上传链路的实现，并设计测试验证可能原因。

改造后的故障注入测试，模拟第一项上传连接断开，后续项目正常发送。诊断可以明确看到：第一项停在上传阶段，记录网络错误；后五项正常提交；批量汇总为五项接受、一项结果未知。

在这个测试中，Agent 可以直接把问题定位到第一项上传，而不必重新检查是否少找、少选了一张。这就是补齐 instrumentation 的作用：把一组待验证的猜测，缩小为有阶段、有对象、有错误码的排查目标。这里的断流是改造后的注入测试，不是对旧事故根因的追认。

定位后，Agent 再根据相同阶段的记录验证改动是否生效，微信端的实际接收效果则继续由我确认。

“工具很慢”，可能慢在初始化

以前，Agent 看到文件工具耗时偏长，需要继续检查启动、通信和查找过程。分开计时后，它可以先比较阶段，再决定去读哪一部分实现。

例如，一次隔离真实模型测试里，查找文件的沙箱初始化约 85 毫秒，执行阶段约 2.8 毫秒。后续发送快照使用了另一个沙箱，它的初始化和执行又是另一组记录。

在这个样本中，初始化明显比执行本身耗时更多。如果要进一步降低这次文件调用的耗时，可以优先评估初始化成本与复用空间，而不是先去重写文件搜索算法。不过，这并不说明初始化就是整个交互的瓶颈；是否值得优化，还要结合完整链路和更多样本判断。

模型也是一样。宿主看到的“等待首次模型事件”，可能包含请求传输、服务端排队和模型处理等因素。没有模型服务内部的数据，就只能确认外部可见的等待区间，不能把它全部解释为推理时间。

“测试失败”，也可能是测试限制了模型的正常探索

有一轮真实模型测试，模型最终完成了原文件发送，测试却没有通过。

原因是测试要求工具调用恰好两次，实际发生了五次：一次读取遇到无效引用，模型重新查询，最后完成发送。

首次无效读取是真实的工具错误，不能抹掉；但随后恢复并完成任务，也是真实发生的。把预设测试中的固定路线套到真实模型上，就会把这种情况误判成整个任务失败。

后来我改成核对独立工具执行记录与 OTel 中的调用序列、次数是否一致，再验证必要的查找、终结发送和附件记录。不强迫模型永远只走两步，也不放弃检查漏记录和重复发送。

这让负责开发的 Agent 有依据修改测试契约，而不是为了让用例变绿，去限制业务模型的正常探索路径。定位更准确，修复就更容易落在真正需要修改的地方。

让这些数据真正帮助 Agent，而不是制造新噪声

实践中，记录的质量与数量同样重要。

我也尝试过文件系统的自动追踪，但后来关掉了。在当时两个隔离真实模型测试样本中，逐文件操作诊断约占总诊断字节的 64%。这只是那两个样本的比例，却提醒我：高频成功操作产生的记录，可能比真正关心的信息多得多。

因此，我保留工具请求边界和沙箱生命周期的观测，不再自动记录每一次 readdir、lstat、realpath。先让 Agent 找到有问题的阶段，确有需要再深入调查，而不是让它每次都筛选大量重复的底层成功记录。

我踩过一个坑：为了统一诊断字段，把未列入白名单的技术错误码变成 other。记录看起来规整了，Agent 却失去了区分故障的线索，又得回到代码和其他日志中寻找答案。后来本地诊断保留已经采集到的原值，不再用模糊分类覆盖具体错误。

另一个要求是验证观测本身。我不仅检查业务结果，也用独立工具执行记录与 OTel 做对账，确认实际调用没有漏记、没有重复记录。前面那轮五次调用的真实模型测试，正是在这样的核对中暴露出固定次数断言的问题。

存储则保持简单：目前使用本地有界 JSONL 和读取器，没有部署独立观测平台。默认保留 7 天，同时限制文件总量和写入队列；容量触顶可能更早淘汰。这样既方便 Agent 直接查询，也控制长期运行的成本。

这些本地记录可能含路径、查询词、标识和 URL，分享前需要检查。我没有额外采集文件正文或模型全文；目标是提供定位所需的证据，而不是把所有内容都塞进日志，再原封不动交给 Agent。

写在最后：给 Agent 更清晰的事实，让它更快做对判断

回看这次改造，OTel 改善的是开发 Agent 的工作方式。

效率上，减少了为了确认“发生过什么”而进行的反复查询和试探。 Agent 可以从一轮交互追到具体工具，再追到对应进程或请求，把调查集中在已经暴露异常的环节。

准确性上，减少了把表象当原因、把连带错误当起因、把测试失败当产品失败的机会。 初始化与执行、首次失效与后续退出、实际工具行为与测试断言，都有了可以分别核对的记录。

修复上，分析和验证有了同一套依据。 Agent 可以根据链路定位要修改的模块，改完后再检查对应阶段和实际结果，不必每次都重新建立一套临时取证方法。

这也是为什么，接入的重点不应停在“安装 SDK”，而应放在 instrumentation：记录哪些公共边界，怎样把一次交互串起来，怎样保留关键结果，又怎样让 Agent 方便地查到它们。

在 Agent 参与开发的过程中，提出可能的原因并不难，难的是从多个解释中选出有事实支持的那个。把执行链路变成 Agent 可查询的证据，就是在缩短从“可能哪里有问题”到“应该修哪里”的距离。这才是 OpenTelemetry 在开发 LLM Agent 工具时带来的核心价值。
