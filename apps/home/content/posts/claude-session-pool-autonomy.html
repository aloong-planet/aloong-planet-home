以前用 Claude Code 跑一个需求，我屏幕上开着好几个终端窗口，一个调度会话派票，几个 worker 会话干活，我在这些窗口之间来回切。这个 worker 做完了，我过去敲 /clear；那个要开 PR 了，我去敲 /compact，敲完再切回调度会话，告诉它「压完了」。还有的做到一半，上下文快满了，就停在那里等我，我敲完 /compact，还得补一句「继续」。

现在我开一个调度会话，交代完需求，就可以走开了。它自己开 worker 会话、派票、收汇报；worker 做完一张票，它把 worker 的上下文清空再派下一张；worker 卡住了，它关掉重开。每个会话都看得见自己的上下文有多大，到了该压的时候自己压缩，压完自己接着干。只有该我拍板的事，比如合并一个改了代码的 PR，它才来问我。

要我亲手做的，只有装一次插件和启动调度会话。这套东西我做成了一个 Claude Code 插件，叫 cc-session-pool。

派活不用人，其余动作都得人来

我的做法是，一个调度会话负责拆需求、派票、收结果，几个 worker 会话各做一张票。会话之间靠 Claude Code 自带的跨会话消息通信，调度会话把票发给 worker，worker 做完把结果发回来。

派活和汇报这一段确实不用人。但真跑起来，我发现自己一直守在电脑前，因为下面这一串动作只有人能做。

  • 开 worker。调度会话没法创建新会话，每个 worker 窗口都得我手动开。
  • 清上下文。worker 做完一张票，上下文里全是上一张票的东西。要在它的窗口里敲 /clear，会话自己敲不了。
  • 压缩。开 PR 前要压缩一下 worker 的上下文，又得我去敲 /compact，敲完还要告诉调度会话「压完了」。
  • 会话自己也压缩不了。一个长任务做到一半，上下文快满了，它只能停下来等我。我敲完 /compact，还得再跟它说一句「继续」。
  • 会话看不见自己有多大。上下文多大，只显示在状态栏上，那是给人看的。该不该压缩，只能我看一眼再告诉它。
  • 调度会话一重启就换名字。Claude Code 每次都给它起个新名字，worker 把汇报发给旧名字，就再也收不到了。
  • 看不见真实状态。worker 可能停在一个权限确认上，可能窗口被关了，调度会话完全不知道，只能干等。

只要我一离开，整条流水线就停。派活归调度会话，剩下这些动作全靠我一件件去做。

把只有人能做的动作交还给会话

拆开看，这些动作分两类。

  1. 管别人的。开 worker、清 worker、压缩 worker、关掉卡住的 worker，这些应该交给调度会话。
  2. 管自己的。看看自己的上下文有多大，太大了就压缩自己，这应该每个会话都会。

所以插件给不同的会话不同的权限。

  • 调度会话拿到一整套管理 worker 的能力。
  • 其他所有会话只拿到管自己的两项能力，看自己的上下文有多大，以及压缩自己。

这样分是有意的。worker 不该能动别的 worker，也不该能动调度会话；调度会话能管所有 worker，但永远不碰它自己的窗口，压缩自己时，它也和别的会话一样，只用管自己的那项能力。权限边界清楚，一个会话出错也波及不到别人。

还有一点，插件只给调度会话工具，不替它定规矩。派哪张票、哪些事它自己定、哪些事必须来问我、什么时候停，都写在我给它的指令里。插件的 README 里有一份示例指令，照着改就能用。

调度会话怎么管 worker

一个目录一个池子

调度会话在哪个项目目录里启动，那个目录就是它的「池子」。池子里登记着它管的每个 worker，登记表存在磁盘上，所以调度会话重启了也还认得它们。

worker 可以由调度会话自己开。它开一个新的终端窗口，启动一个会话，等它就绪了再登记进来。也可以是我之前手动开好的，调度会话直接接管过来，以后用同样的方式管。

命令只能从输入框进去，那就去输入框里敲

要从会话外面清空或压缩一个会话，只能往它的输入框里敲命令。所以插件没有绕路，直接在 worker 的终端窗口里替人敲这条命令。

也正因为要往终端窗口里敲字，管 worker 的这一套目前只支持 macOS 自带的「终端」。压缩自己通常不用往窗口里敲字，也就不受这个限制，后面会讲到。

敲进去以后，还得确认它真的生效了。我的原则是敲完不等于做完，要看到证据才算。

  • 清空之后，会话会换一个新的身份编号。看到编号变了，才算清空成功。
  • 压缩之后，会话记录里会出现一次压缩。看到这条记录，才算压缩成功。
  • 等不到这些证据，就如实报告没有确认，不会再敲一遍。万一第一遍其实生效了，再敲一遍就是重复操作。

状态以 Claude Code 自己的为准

调度会话随时可以看每个 worker 的真实状态，有空闲、正在干活、停在某个确认上（还会说清楚在等什么）和已经不在了四种。这些状态来自 Claude Code 自己的记录，插件只是把它读出来。

有了状态，调度会话就能自己处理异常。某个 worker 卡住了，或者干脆没了，它就把这个 worker 关掉，在同一个名字下重开一个。worker 的名字不变，后面派活的流程也不用变。

只有 worker 停在权限确认上时，它不替我处理。调度会话能看见、能报告，但不会替人点「同意」。替人点确认，等于把权限交了出去，我不打算这么做。worker 默认用 auto 模式启动，停下来等确认的情况会少很多。

调度会话的名字固定下来

调度会话通过插件自带的启动方式启动，每次重启都用同一个名字。worker 汇报时写的收件人一直有效，不会因为重启寄丢。

最难的一环是压缩自己，然后接着干

管 worker 的那一套，做的是替人敲命令，再确认结果。压缩自己难在两处。

第一，不能在干活的时候压。会话是在一轮回答进行到一半时决定要压缩的，可 Claude Code 只在两轮之间压缩对话，一轮还没结束就压不了。所以压缩要排在这一轮结束之后。

第二，压完之后要有人叫醒它。压缩完成后，会话就安静地停在那儿，等人说话。如果没人说「继续」，前面做得再好，流水线也在这里断了。

解法分三步。

  1. 会话调用压缩自己的工具，马上得到答复，说这一轮结束后压缩，压完会叫醒它。然后它把这一轮的话说完。
  2. 这一轮一结束，插件让 Claude Code 压缩这个会话的对话。
  3. 压缩完成，插件替人开始新的一轮，告诉它：「你要求的压缩已经完成，这不是错误，继续刚才的工作。」

这句话是固定的。插件不替会话决定接下来做什么，接下来做什么，会话自己根据压缩后的摘要判断。

插件里有一段代码直接跑在 Claude Code 内部，压缩和叫醒都由它在里面完成，不需要往窗口里敲任何东西。所以这条路对任何会话都有效，不管它跑在哪个终端里，也不管是不是调度会话开出来的。在那段代码跑不起来的会话里，插件退回另一条路，往窗口里敲 /compact，压缩完成后由一个钩子叫醒会话。

我在自己的会话里试过。说一句「自己压缩一下」，它回答完这一轮，压缩不到一分钟，压完 1 秒之内它自己开了新的一轮，把刚才没做完的事接了下去。

这里有几个坑，都是实测踩出来的。

  • 输入框里有字的时候不能敲。走敲命令那条路时，如果用户在输入框里打了一半字，敲进去的压缩命令会和那半句话粘在一起，变成一条普通消息发出去，压缩根本不会发生。所以插件敲完会去会话记录里核对，看命令是不是单独排进了队列。如果是和别的字粘在一起的，就明确报错，并说明这次不会压缩。
  • 人中断了，就不压。那一轮被人打断，或者因为出错而结束，压缩就取消。人既然插手了，就不该再自作主张。
  • 子 agent 不替主会话压缩。插件内部那段代码接手调用时，会拒绝子 agent 的调用；走敲命令那条路时，插件分不出调用来自谁，会照样压缩整个会话，所以 README 的示例规则里写明子 agent 一律不调用。只有会话本身，才最清楚自己什么时候该压缩。
  • Claude Code 自己触发的自动压缩，不叫醒会话。只有会话自己要求的压缩，压完才叫醒。否则会凭空多出一轮。

什么时候该压，会话得先看见自己有多大

会话能压缩自己之后，马上要回答的是什么时候该压。

先说为什么要压。模型没有记忆，每发一次请求，都要把整段上下文重新读一遍。所以一个会话的消耗，大致等于请求次数乘以每次的上下文大小。一张大票做到后半程，上下文能涨到几十万 token，哪怕只跑一条很小的命令，也要为这几十万付一次读的钱。压缩做的，就是把这个乘数变小。

但压缩不是越勤越好，它本身也有成本。

  • 缓存要重写。压完之后，对话的开头变了，缓存里原来那份用不上，压缩后的内容得整份重新写进缓存。写缓存的单价是读缓存的几十倍。
  • 压完也小不到哪去。压缩后要重新载入规则和用到的 skill，压完的第一个请求，上下文通常就有 10 万左右。

所以压缩是一笔先付钱、后回本的账。上下文越大、压完之后剩下的活越多，越划算；上下文不大、又快收尾了，压了反而亏。

我把最近 30 天里 294 次手动压缩（压缩前都在 10 万 token 以上）拿出来算了一遍，比较压缩之后那一段的实际花费和假设不压缩时的花费。总的来看省了 37%，但分开看差别很大。

我的开发流程里，交付前和合并前各有一次固定的压缩。在我的会话里，交付这一步大约三十来次请求，正好落在图里左边那一列。所以我定了一条规则。到了这两个点，上下文不到 20 万的不压，直接往下做；20 万及以上，才压。

规则定下来，新的问题又来了，会话不知道自己有多大。上下文的大小显示在 Claude Code 的状态栏上，那是给人看的，模型看不见。要按 20 万来判断，还得我看一眼状态栏，再告诉它要不要压。

所以插件又给每个会话加了一个工具。调用它，就能拿到状态栏上的那个数，包括最近一次请求的输入有多少 token、模型的上下文窗口有多大、已经占了几成。这个工具同样由那段跑在 Claude Code 内部的代码提供。

有了这个数，要不要压也不用问人了。会话到了交付前，先看一眼这个数，不到 20 万就直接交付，20 万以上就自己压缩，压完被叫醒，接着交付。用不了这个工具的会话，就从自己的会话记录里把这个数算出来；实在查不出，就照常压缩。

一张票的完整生命周期

把上面这些拼起来，一张票从派出到收尾要走六步。

  1. 调度会话看看池子里谁空闲，没有空闲的就新开一个 worker。
  2. 通过跨会话消息把票发给 worker。
  3. worker 开始干活。上下文涨大了，它自己压缩，压完接着干。
  4. worker 做完，开 PR 之前先看一眼自己的上下文，20 万以上就自己压缩，压完接着开 PR；不到 20 万，直接开。
  5. PR 开出来以后，只改文档的自动合并；改了代码的，调度会话拿来问我，我批准了它再合。合并后，它清空这个 worker 的上下文，派下一张票。
  6. 途中 worker 卡住或者没了，调度会话把它关掉，在同一个名字下重开。

这六步里，机械的动作没有一个需要我。需要我的只剩该我拍板的事，比如批准合并、确认权限，而且都由调度会话来找我。

写在最后

如果你也在用一个调度会话带几个 worker 会话干活，可以先数一数。一个需求跑下来，你亲手敲了几次 /clear 和 /compact，说了几次「继续」，又替它看了几次状态栏。这些就是你的流水线停下来等你的地方。

cc-session-pool 是开源的，安装方法和示例指令都在 GitHub 仓库的 README 里。
