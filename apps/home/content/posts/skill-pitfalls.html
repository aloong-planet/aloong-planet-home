我维护了十几份 skills 来实现从需求到交付的完整闭环,在做两个较为复杂的项目时,单个长时自动化开发任务的 tokens 逐渐累积达到百万甚至千万级,整个 session 会经历数次到数十次的内容压缩,skills 的坑几乎踩了个遍:有时 agent 根本不触发某个 skill;有时前半段执行得很好,后半段就开始自由发挥;有时照着同一份 skill 办事,这一次效果好,下一次效果就不理想。

于是我研究了官方的 skills 写作规范,以及社区的一些最佳实践,开始不断地评估和迭代我的 skills,最终达到了稳定的效果。如果你在使用 skills 的过程中也碰到这样那样的问题,相信看完这篇文章,一定会有所收获。

首先我们需要明白 skills 的一些机制。一份 skill 从写下到生效,要过三道关:「被触发、被记住、被执行」。每一道关都有自己的失效机制,每个机制都对应大模型的一种确定行为。懂了机制,评估和优化才有抓手。

第一道关:触发——它可能根本没打开你的文档

最早的困惑是:明明写了 skill,agent 却像没看见。

机制在平台那一侧:skill 的加载不是查表分发,是语义匹配。每份 skill 只有 frontmatter 里那句 description(选择器)常驻上下文,正文要等被选中才加载。模型拿你的对话和这句话做匹配——这是个概率行为,不是 if-else。

于是两种写法悄悄杀死你的 skill:一种是「帮助处理多语言问题」式的空泛用途,没有任何具体场景词,模型匹配不上;另一种更隐蔽——把正文流程摘要塞进 description,看似贴心,实际上摘要占掉的字符稀释了触发关键词的密度,而且执行指导被放进了一个只在「要不要加载」那一刻起作用的字段。正文被触发后本来就会完整加载,预告纯属浪费。

优化落成一句判据:遮住正文只读选择器,应能回答「什么时候该用它」,且推不出「具体怎么做」。再加一层工程兜底——触发是概率,显式调用是确定性,关键路径上的 skill 在工作流里按步点名调用,不赌自动匹配。

第二道关:记忆——它记得的那份,不是磁盘上那份

第二类事故更隐蔽。同一个会话里,agent 拿着一份 skill 的旧版本做判断——而磁盘上那份早就更新过了。

机制是两件事叠加。长会话会触发上下文压缩,早前加载的 skill 正文被摘要化、截断——这是第一件。第二件更关键:模型没有「我忘了」的信号。它不知道自己记忆里那份是降质版,它只是继续用,理直气壮。人忘了东西会迟疑,模型不会——降质的记忆和完好的记忆,在它那里手感完全一样。

还有一种丢失更主动:模型有时不走加载机制,而是自己拿 head -100 这类命令去读 skill 文件——前一百行进了上下文,后面的内容从未被加载,skill 就只生效了一半。它对此同样毫无感知:读了一部分和读了全部,在它那里没有任何区别,只是缺的那部分规则永远不会被执行。我翻过官方文档和社区实践,结论是:现阶段没有任何机制能保证模型完整加载一份 SKILL.md。

既然平台不兜底,解法只能是纪律,我写进了全局配置:读 skill 一律走 Skill 工具(coding agent 自带的内置工具,由平台载入 skill 全文),上下文压缩后同样重新调用,不改用文件读取;禁止一切部分读取——读一半给出的是「我看过了」的假确定感;审计或修改任何 skill 之前,先读磁盘上的权威现状,不信上下文里的缓存。

第三道关:执行——全文读了,行为还是飘

前两道关是平台机制,绕得开。第三道才是深水区:skill 全文都加载了,agent 也认真读了,行为还是飘——同一份 skill,不同会话执行出不同的结果。

是文档的问题,还是模型的问题?吵不出结论,得测。这也是标题里「评估」的答案——我用的方法很朴素,任何人都能照搬:

把要评估的 skill 冻结,派三个互相隔离的 agent 按它执行同一个任务,比较三方的产出差在哪。如果 skill 写得足够好,三方应该给出同样的结果——收敛度,就是 skill 质量的读数;每一处分歧,都精确指向 skill 里的一个缺陷。

我拿自己的审查规范当靶子跑了十几轮:三方发现的交集从 0 收敛到 10;逐轮记录里,每一处被定向修复的分歧点都在下一轮消失,没有出现过反例。但轮次不是重点,重点是分歧背后暴露的机制——归拢起来四个,每个都对应大模型的一种底层行为。

  • 机制一:歧义不会被上报,只会被填充。第一轮交集为零。回头看规范里的判据——「指代要有锚点」「限定词不要丢」——每一条都对,每一条都不可判。大模型碰到歧义不会停下来问,它挑一个高概率的解释继续走:三个实例,三套解释,每套单看都说得通。规范里每个没写死的地方,都是裁量权的无声下放。解法:判据必须当场可判——补上可执行判据后,同一处文本三方立刻同判。
  • 机制二:它服从的是字面,而每个字都要过它自己的解释器。我要求「逐条编号列出全部条文」,三个 AI 都认认真真照做了,交回来的总数是 76、47、63——三套。没人偷懒,没人违规,只是「条文」这个词没定义:规则先被模型逐词解释、再被执行,解释的自由度原样变成行为的自由度——一条规则可以被完全遵守而完全不起作用。解法:把规则依赖的每个词定死。「条文」钉成「一个列表项、一个独立段落、表格的一行,各算一条」,三方立刻收拢。
  • 机制三:没被要求的内容,不是被隐瞒,是从未被生成。有一轮报告显示「三方相反裁决归零」,漂亮得可疑。加一条要求——检查表里每项都要留结论,不许只报命中——四处隐性分歧立刻现形。模型的输出是按需生成的,格式没要求写的它就不写,于是「漏看了」和「看过判合规」长得一模一样:测量方式本身在制造结论。解法:产出格式逼出全量结论,让「没看」无处遁形。
  • 机制四:它在字面约束下寻优,而它的语言学比你好。我规定「代入指代后意思变了也算失锚」,一个 agent 答:「这是转喻,不算」——转喻是真实的修辞学概念。我补一条「不得以转喻开脱」,下一轮,两个 agent 分别搬出「桥接指代」和「泛指占位名词」,同样真实,规则字面全满足,豁免的还是同样三处。这不是狡辩,是约束求解:只要满足字面的合法路径存在,模型就能找到,它的语言学范畴库比你深。解法:判文字的规则,通则不收敛,只能形态清单逐个封。反向验证过一次——把七条指代细则压成一条通则,检出率从 10/10 掉到 3/10,怎么补通则都救不回来。那份越写越长的清单不是过拟合,是开放集合的已知成员。

优化的起点:常见的改法为什么不够

发现 agent 又犯了同一类错,顺手对它说:「把这个教训更新到对应的 skill 里。」它答应得很痛快,diff 看着也合理,这事就算完了——这是第一层。

稍微谨慎一点,加一句:「再 review 一下,确认改得没问题。」模型认真读一遍,回复「没有问题」,偶尔挑出一两处小毛病——这是第二层。

再往上,按官方文档推荐的方式做评测:准备一批查询测触发率,跑 baseline 对照看装上 skill 后任务成功率有没有变化。我照做过——20 组查询测触发,baseline 对照下某条款的成功率从 0/5 拉到 5/5。它们确实有用,能抓住「选择器写坏了」和「skill 整体没起作用」这两类问题——这是第三层。

三层都做了,还是不够。因为它们都没碰到真正的病灶:模型往 skill 里塞新内容的方式,本身就是新问题的来源。

我在实测里反复看到同一批行为:发现一条新教训,模型倾向于找个看起来相关的地方直接塞进去——多数时候是「正在编辑的那一节的末尾」,位置是顺手的产物,不是判断的产物;它不查这条规则是不是已经在别处写过,于是同一规则出现两份,将来改一处漏一处;不比对新条文的适用面和所在节的适用面,于是通用规则被埋进具体小节,读者按小节缩小它的适用范围;也不核对新条文和同批新增的其他条文有没有冲突。

而第二层的 review 接不住这些:review 的注意力天然落在「新改动 × 已有内容」上,新条文彼此之间没有触发点;更何况,没有机械化清单的 review 本身就不收敛——这正是那十几轮实验测出来的东西。

第三层的评测也接不住:触发率和端到端成功率看不见「内部有两份会各自腐烂的规则」这种病,它要再过几十个 session 才发作。

所以真正的优化不是一次动作,是一套方法。我把它沉淀成一份管 skill 的 skill——skill-policy,拆开是三层:怎么写、怎么改、怎么 review。

第一步,怎么写:每条规则都要接得住那四个机制

写作层的规则,每一条都能回溯到前面某个机制:

  • 每条规则自带当场可判的判据(堵机制一):「指代要有锚点」不合格,「在上文指得出一个名词性词组,代入后意思不变」才合格——判据可执行,三个 agent 才会给出同一个裁决;
  • 规则依赖的每个词都定死(堵机制二):写「逐条编号」就要同时写清什么算一条;写「列全」就要给出不依赖覆盖率的枚举手段——没定义的词,解释自由度就是行为自由度;
  • 产出型条文要求逐项留结论(堵机制三):凡是清单式检查,要求对每一项写「过/不过」,不许只报命中——让「没看」无处遁形;
  • 判文字的规则配形态清单(堵机制四):判定对象是自然语言本身时,通则不收敛,把已知的豁免形态逐个枚举,并明写这是开放集合、遇到新形态就补一条;
  • 几条通用纪律:条文用命令式,主语是执行者的动作;软化词(一般、通常、尽量)出现在规则里即违反——例外要写成「仅当 A 且 B 时可 X」的触发条件;节标题是一个断言,条文挂进哪个节,位置就在替它声明适用面——入节前先比适用面;流程类条文按执行顺序排列。

第二步,怎么改:修改比新写更危险

新写一份 skill 时人是警觉的,改一份旧的时人是顺手的——塞歪的规则几乎都出生在「顺手」里。改的纪律:

  • 改前留快照:冻结基线,改完把前后条文集合做差,差集必须只包含声明过的改动——防止顺手夹带;
  • 新教训先抽象成规则再进入:写进 skill 的是规则,不是事件经过——删去日期和项目名后条文还完整、还可执行,才算抽象完成;
  • 同一规则只留一份正本:别处需要就用指针指过去,不复制——两份一样的文本只是此刻一致,改了一处另一处不会跟着变,而改的人不会想起去查另一处;
  • 同批新增的条文互相对读:review 的盲区就在这里——注意力天然落在新改动与已有内容之间,新条文彼此没有触发点。我自己就有过三次同一个提交里自相矛盾的记录,最典型的一次:新写的引言说「这个声明没有读者会去核」,而同一批新增的检查条款,恰恰就是核它的读者;
  • 动过手就重跑整轮检查:改动是否带进新问题,不重跑一遍是不知道的。

第三步,怎么 review:两阶段自检,加隔离复验

单遍通读式的 review 不收敛,有效的做法分两个阶段,而且顺序是硬的:

  • 阶段一,逐条审措辞:对每条条文问五个问题——是命令还是描述?删去人事时地还成立吗?判据能当场执行吗?指代和术语有锚吗?限定词丢了吗?凡可枚举的检查(指代、软化词、术语)先全量提取成表,再逐项判,每项留结论。循环到一整轮零发现。
  • 阶段二,跨条文对读:按「它在约束什么」把条文归堆,堆内逐对给出「相容/冲突」结论;节标题也当条文取适用面,与节内逐条比包含;流程节标上执行序,与书面序两列对照。它必须排在阶段一收敛之后单独跑,因为单看每条都正确、合起来才互相锁死的冲突,在逐条审里永远不会现身——跑多少轮都一样。
  • 关键节点,隔离复验:就是第三道关里那个收敛度测法——派几个互不可见的 agent 按同一标准执行,分歧不是吵架,是坐标,每一处都精确指向 skill 里的一个缺陷。修分歧,再循环,直到一整轮零新增发现。

这套流程管用吗?效果非常明显:

  • 缺陷密度降了:一份用了很久的核心 skill,第一次按规范全量体检揪出二十七处问题——重述、失锚、冲突、错位都有;修完再派三个隔离 agent 复验,只剩一项三方全票的缺陷,恰好是人工修复漏掉的那处,被复验兜住。
  • 行为稳定了:最早三个 agent 审同一份文档,发现交集为零,每人一套答案;十几轮迭代后收敛到十。开篇说的「这一次效果好,下一次效果就不理想」基本消失——多会话执行,终于像在执行同一份文档。
  • 流程能自愈:有一轮修复,一口气改了十几处问题,按「动过手就重跑」的规矩再跑一遍自检,又抓出四处「修复自己引入」的新毛病——比如把重复的规则改成指针时,顺手把被指向的内容也搬了过去,造出一份新的重复。修复会制造新缺陷,这几乎是必然;区别在于流程让新缺陷活不过下一轮。连修复动作本身都被流程看着,这比任何单次结果都更能说明方法在工作。

丑话也说全:严格意义的「三方完全一致」从未达成,残余分歧全落在「某个词算不算名词性词组」这类语感层判断上。规范能把分歧从「每处都吵」压到「只剩语感」,但语感的地板就在那里。

这套流程贵吗?比「顺手塞进去」贵得多。但另一边的账更贵:一条被塞歪的规则不会报错,它可能会在之后每一个 session 里安静地歪着执行,把问题埋在你不知道的角落——当哪天你发现不对劲的时候,需要花更大的代价去找原因和修复造成的一连串问题,倒不如先花点时间从源头上解决它。

写在最后

回头看,这些机制没有一个是 AI 的缺陷。歧义被默认值填满、每个词都要过解释器、格式决定产出、规则的缝被合法地钻过去——这些从来就是「用自然语言约束执行者」的固有问题,人类组织里它们同样每天发生,只是人类同事会用常识悄悄把裂缝补上,补完也不会跟你提一句。

AI 会跟你汇报自己做了什么,只是不会告诉你,它把你那句话理解成了哪个意思——补的动作发生在理解层,汇报只到动作层。于是你拿到一份挑不出错的执行记录,看不见的是它替你做的那些默认选择。这也正是要派几个 agent 并排跑的原因:单看一份报告永远无懈可击,差异只在并排时才现形。而完全一致原理上就做不到——每一次生成都是一次采样;规范能做的,是把可选的解释压到足够少,让它们尽可能得出同一个结论。

所以,当你的 skill 没有按预期工作时,问三个问题:它被触发了吗(选择器写对了没)?它被完整记住了吗(压缩后重新加载了没)?它被一致地执行了吗(拿收敛度测过没)?三道关排查下来,你多半会发现——skill 是一面镜子,照出的不是 AI 的毛病,是自己的规范从来就有多少歧义。

附:完整的 skill-policy,以及怎么用它

下面是我实际在用的那份规范全文,以及它的用法。前面讲的四个机制和三步方法,落到文件上就是这一份——你可以直接拿去用,不必从零推一遍。

怎么装

Claude Code 和 Codex 的目录约定不同,但形状一样——一个以 skill 名命名的目录,里面放 SKILL.md,目录名必须和 frontmatter 里的 name 一致:

全局(所有项目)单个项目
Claude Code~/.claude/skills/skill-policy/SKILL.md<项目根>/.claude/skills/skill-policy/SKILL.md
Codex~/.agents/skills/skill-policy/SKILL.md<项目根>/.agents/skills/skill-policy/SKILL.md

这份规范是纯写作规则,不依赖任何一边的工具,两个 harness 可以共用同一份文本。顺带一提,全局指令文件也是对应关系:Claude Code 的 CLAUDE.md 对应 Codex 的 AGENTS.md,前面那几条「读 skill 必须完整加载」的纪律写进它就行。

两边都在用的话,装一份、另一处做软链,不要复制两份:

mkdir -p ~/.agents/skills
ln -s ~/.claude/skills/skill-policy ~/.agents/skills/skill-policy

复制两份的下场我自己撞过:两处同名、连行数都一样,内容却早已不同——改了一处,另一处不会跟着变,而改的人不会想起去查另一处。这正是规范里「同一条规则在两处各写一遍即为缺陷」说的事,它对规范自己同样成立。

装完开一个新会话,说一句「按 skill-policy 审一下某某 skill」,能自动加载就说明选择器工作正常。别在旧会话里验证——旧会话不会重新扫描 skill 目录。

description: "skill 写作规范。创建或修改任何 skill(全局 ~/.claude/skills 或项目 .claude/skills,含 SKILL.md、引用文档、资产说明)之前激活。"
when_to_use: "另在 review 既有 skill 的措辞与条文一致性、排查条文间矛盾时使用。"

# Skill 写作规范

适用于一切 skill 的新建与修改:SKILL.md、其引用文档、资产内的说明文字。

**条文的单位定死**——一个列表项、一个独立段落、表格的一行,各算一条;标题与代码块的语法内容不算,**代码块内的说明文字**(模板占位符里的指导语、代码注释)照常成条——算不算条按内容定,不按围栏定;同一空行块内以硬换行并置的行各算一条,行尾不是 。!?;: 及其后的引号、括号、强调星号的行是排版折行,与下一行同属一条;列表项的缩进续行随其列表项。

## 1. 条文必须是命令式的明确语句

- 用「必须 / 不得 / 一律 / 缺任一则不得 X」陈述;主语是执行者的动作,不是现象。
- 每条规则自带可执行判据:读者无需任何额外上下文即可判断"此刻是否违反"。
- 不得用现象描述代替规则:"X 会发生"不是规则,"不得做导致 X 的 Y"才是。
- 凡判据要求"举得出一个例子",先找它的可枚举结构改成照表核对:构造例子依赖灵感,灵感不可复现;对齐表只依赖眼睛,且检出率更高。
- 指代与本 skill 自定义的术语,使用处必须有锚。**判据**:在上文指得出锚点——指代词的锚是一个名词性词组,术语的锚是给出其判据或构成的定义条文(仅出现名字不算)——把锚代入该处后句子仍读得通、意思不变。锚不存在即失锚,锚只在后文即倒置,代入后意思变了即同名异义。带显式出处的引用(「按 §N 的…」「见某节」)不算倒置——它自带定位,不需要上文。
- 泛化或收紧措辞时,原有的限定词不得丢。**判据**:去掉它后试举一个「符合新表述、但机制不成立」的反例——举得出,它是条件,必须留;举不出才是载体,可以删。

## 2. 实例必须抽象成规则后才准进入

- 促成规则的事故先抽象:写进 skill 的是抽象后的规则,不是事件经过。
- 抽象完成的判据:删去日期、**事发**项目名、当事文件名后,条文仍完整、仍可执行。删的是事故的身份,不是被测技术的名字——后者可能是判据的前提,按 §1 的限定词测试判去留。
- 事件叙事另有归宿:项目复盘文档或 memory;skill 内不得保留"某日发生过某事"式内容。
- 例外必须写成触发条件("仅当 A 且 B 时可 X"),不得写成豁免叙事。**软化词(一般、通常、多半、尽量、原则上)出现在规则里即违反本条**:要么写出例外的触发条件,要么删掉软化词——它把例外藏了起来,读者无从判断自己是不是例外。出现在理由或举例里不算。
- 理由允许保留,但必须是**机制性**的且并入条文本身;不得以括号轶事、事件叙事的形式追加。
- **不加纯出处标记**:「(某日定案)」这类只标何时定、不承担任何判据前提的日期标注,一律不写;既有的,触碰其所在条文时一并删。何时定的不改变执行者此刻该做什么,考据归版本历史。作为实测数据适用前提的日期不算出处标记,按下一条办。
- 支撑技术判断的**实测数据**(量级、比值、行为差异)视为判据的一部分,可以保留;须标注其适用前提,不得叙述取得它的过程。**判据**:能在同一处指出哪句话是前提即合规,不要求特定句式、也不要求单独成句;指不出才算缺前提。

## 3. 条文的位置与顺序(写入时就定)

**节标题是一个断言**:条文挂进哪个节,位置就在替它声明适用面。

- **入节前先比适用面**:问新条文「它在约束什么」,再拿同一个问题问目标节的标题与引言;条文的适用面不落在节的适用面之内,不得入该节——嵌套时逐层都须成立;比节宽的上提一层(外层节或文首),无处可去的先立节。不得因为"正在编辑这一节"就把条文追加在节尾——增量修改的默认动作恰是顺手追加,位置从来不是判断的产物。
- **流程类条文按执行顺序排列**。**判据**:给每条标执行序,与书面序两列对照,乱序即违反本条。

## 4. 选择器(frontmatter)的写法

**`description` 与可选的 `when_to_use` 共同构成选择器,下列条文对两者各自生效——唯「做什么」一项只要求 `description` 写明,`when_to_use` 按其定义只补触发场景。** 写了 `when_to_use` 就必须与 `description` 分工:只补 description 没覆盖的触发场景,不得复述它已经说过的话——两个字段都常驻上下文,复述一遍等于把同一份匹配预算花两次。

- 必须用第三人称陈述;出现「我 / 你」即违反。
- 必须同时写明「做什么」与「何时触发」,触发条件用具体场景词;只写用途不写触发,或用「帮助处理…」式空泛措辞,均视为未完成。
- 不得概括正文的规则、流程或步骤;流程只准在正文里出现。**选择器只负责被选中**:两个字段都常驻上下文,唯一职责是让模型从全部可用 skill 中选中该用的那个;正文在 skill 被触发时必定完整加载,不需要在此预告。写进流程摘要要付两笔代价——一是占掉本该用于匹配的字符、从而稀释触发关键词的密度,二是把执行指导放进一个只在「要不要加载」那一刻起作用的字段。(依据:官方 Agent Skills 文档对 description 的定位与 progressive disclosure 机制。)
- 判据:遮住正文只读选择器,应能回答"什么时候该用它",且推不出"具体怎么做"。

## 5. 自检(两阶段,阶段一收敛后才准进阶段二)

### 通则(两阶段都适用)

**两种用法,只差范围**:改完自审时,范围由本次改动圈定;**审一份没动过的 skill 时范围由文件圈定**——阶段一过全部条文,阶段二拿每一条问「它在约束什么」取对象。后者不得只盯可疑处抽查:抽查漏掉的正是"两条都没被怀疑、合起来才冲突"的那类。无修改授权的评估,收敛判据读作「一整轮下来零新增发现」——发现只记录不清零。

**管辖面是整个 skill,不止 SKILL.md**——SKILL.md 对某个资产的**描述**与该资产自己的说明尤其容易对不上。**判据**:枚举该 skill 管辖的全部文件——目录内的引用文档,**加上正文或引用文档里以路径引用的资产**(资产常放在多个 skill 共用的目录下,按目录枚举必然漏掉它们)——对本次未触碰的每一个也给出「需不需要跟着改」的结论;答不上来的文件,就是没审。

**凡可枚举的检查,先全量提取成表,再对着表逐项判**(指代、软化词、条文清单皆然)——通读着找必漏,而漏掉的那条不会自己现身。**表里每一项都要留下结论**,不得只报命中项:只报命中时,「漏看了」与「看过判合规」在产出上无从分辨,而前者恰恰是要防的。

**顺序是硬的。** 阶段一每次只有一条条文在视野内,**单看每条都正确、合起来才互相锁死的冲突在其中永远不会现身**——跑多少轮都一样,而"已经审过 N 轮"恰恰会盖住它;阶段二必须排在阶段一收敛之后,因为改措辞本身就会造出新的冲突。

### 阶段一 逐条审措辞,循环到收敛

对在审范围内的每条条文(不论落在 SKILL.md、引用文档还是资产说明里)逐一问:
- 是命令还是描述?描述 → 改写为命令或删除。
- 删去具体人、事、时、地后还成立吗?不成立 → 抽象未完成,继续提炼。
- 判据能当场执行吗?不能 → 补判据,或整条删除。
- 句中的指代与自定义术语有锚点吗?判据见 §1 的锚点规则 → 失锚则补锚点或改写成直述,倒置则前移定义。
- 泛化或收紧措辞时,原有的限定词丢了吗?判据见 §1 的限定词规则。**审既有 skill 时本条读作**:条文有没有作出它的机制支撑不了的断言,用同一个反例测试。但**只对承载判据的条文生效**——举例与机制性理由里的陈述即便偏宽,若不改变读者该做的动作,记录即可、不动手;**只有当过宽会让读者少做该做的事时才必须改**。

**这一轮只要动过手,就得重跑整轮**——改动是否带进新问题,不重跑一遍是不知道的。**改了某节的标题、引言或适用范围,该节全部条文都算被改动**,逐条重审。**收敛判据:一整轮下来零发现**,这一阶段才算完成。

### 阶段二 对读

**先归堆,不要两两穷举全文**:拿每条条文问「它在约束什么」,答案即受约束对象;把约束同一对象的条文归到一堆(不论同节异节)。堆通常只有两三条,而穷举会把工作量推到没人跑得完,跑不完的检查等于没有。

**归堆必须可核,不是抽查**:按开头定死的条文单位逐条编号列出,每条至少归入一个堆,末了报出「条文总数 / 堆数 / 各堆成员编号」。有条文一个堆都没进,就是还有对象没被取出来。

**节标题也入审**:把每个节标题与引言当条文取适用面,节内逐条与之做包含比对(嵌套逐层)——条文适用面不在节适用面之内即错位(违反 §3),上提或换节。

堆内逐对给出「相容」或「冲突」结论——**每一对都要留结论**,不只报冲突的。判定冲突的,要么改一方,要么补一条写明前提的条文使两者相容。

**冲突的判据**:举得出一个具体情形,使两条**无法同时满足**、或该情形**落不进任何一支**,即为冲突;每种情形都有唯一归宿、只是措辞宽窄不同则为相容。一条给分类、另一条给归属时,把分类的每一项与归属的每一支列成两列对齐,任何一项找不到唯一归宿即为冲突。

**同一条规则在两处各写一遍即为缺陷**,不因两处措辞一致就放行——一致只是此刻一致,改了一处另一处不会跟着变,而改的人不会想起去查另一处。**判据**:删掉其中一处,规则是否仍完整可执行?是 → 那处是重述,改成指针或删掉。

本阶段的每次改动都退回阶段一过一轮,再重跑本阶段,直到两阶段都零发现。

怎么用:一次完整的写、改、审

规范本身是条文,下面是拿着它把事做完的流程——你说什么、它交回什么、你核什么、什么算完。

写一份新 skill

新 skill 几乎都不是凭空写的,而是从当前会话里长出来的:刚踩了一个坑,或者刚发现一个反复出现的模式。上下文都在,不用开新会话:

  1. 总结和复盘:在当前会话里把刚发生的事说清楚——出了什么问题、根因是什么、以后期望怎么做。这一步是原料,先别谈规则。
  2. 让模型出详细方案:不写正文,先出方案——这份 skill 要约束什么、什么时候该触发、分几节、每节管什么。要它写成能逐条确认的形式,不是一段概述。
  3. 人工确认方案的细节:你核的是它核不了的——这个结构是不是你想要的、有没有你在意但它没听出来的边界、有没有把只在某种条件下才成立的坑写成了通用规则。方案里读着别扭的地方,多半是它替你补了一个默认值。
  4. 使用 skill-policy 把方案抽象成 skill:说「按 skill-policy 把这份方案写成 SKILL.md」。措辞、抽象程度、条文位置、选择器写法都由规范管住,你不用逐条盯。
  5. 使用 skill-policy 复核,加人工复核,直到收敛:说「按 skill-policy 的 §5「自检」审一遍,报告要带中间产物」——检查表和归堆表,不只是结论。你抽查表里判「合规」的两三条,自己按判据走一遍;有发现就改,改完重跑,直到一整轮零发现。
  6. 使用新的 skill:开一个新会话,说一句触发场景,能自动加载就成。这是全流程唯一需要新会话的地方——当前会话不会重新扫描 skill 目录。

更新一份已有 skill

流程完全一样,只有第 2 步的产物不同:模型出的是修改方案——改什么、加到哪一节、为什么、动了哪些既有条文。另外第 1 步的复盘要从读磁盘上的现状开始,不信它记忆里那份——第二道关说的就是这个。其余各步不变。

审一份没动过的 skill

别人写的、或自己很久没碰的,直接从第 5 步进:说「按 skill-policy 的 §5「自检」审整份 X,报告要带中间产物」。读报告先看表全不全,再看发现——表不全的报告,发现不可信。评估不改文件,发现只记录不清零,所以收敛看的是有没有新增,不是有没有发现。要加固就派两三个互不可见的 agent 各审一份副本,比发现的交集:全票的必修,分歧的你来裁决。每条发现最后都要落到三种归宿之一:修、记录不动、驳回并写明理由。
